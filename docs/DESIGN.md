# Семантический поиск по коду: локальный демон + MCP

Технический документ реализации. Версия 1, 2026-08-06.

---

## 1. Задача

Дать Claude Code инструмент поиска **по смыслу**, а не по строке.

Два сценария, ради которых всё затевается:

1. **«Где обрабатывается повторная отправка платежа?»** — grep по `retry` даёт двести
   совпадений, grep по `payment` — тысячу, а нужная логика лежит в
   `src/lib/queue/backoff.ts::scheduleRedelivery`. Слово не угадать.
2. **«Где ещё в монорепе делается то же самое?»** — три реализации одной логики,
   названные по-разному. Grep их не покажет принципиально.

**Не является заменой grep.** Точный поиск по имени символа grep делает лучше и быстрее.
Рабочая схема — гибрид: семантический поиск сужает область до 5–8 мест, дальше точный
поиск и чтение внутри неё.

### Отношение к LSP: дополнение, а не конкурент

У Claude Code есть официальные плагины code intelligence на базе LSP
(`/plugin install typescript-lsp@claude-plugins-official`) — девять операций, включая
переход к определению, поиск ссылок, реализации и call hierarchy.

Соблазнительно считать их «худшей версией» семантического поиска. Это не так: они
отвечают на другой класс вопросов, и разница не в качестве, а в природе гарантий.
**LSP точен и полон над графом типов; эмбеддинги приблизительны и полноты не гарантируют.**

| Вопрос | LSP | Эмбеддинги |
|---|---|---|
| Кто вызывает `scheduleRedelivery`? | **все** вызовы, гарантированно | 5 похожих, без гарантии полноты |
| Что сломается при смене сигнатуры? | точный ответ | не отвечает |
| Где определён символ? | одна точка | приблизительно |
| Где обрабатывается повторная отправка платежа? *(имени не знаю)* | **не отвечает** — нужен символ | ядро задачи |
| Где ещё делается то же самое? *(названо иначе)* | **слеп** | ядро задачи |
| Как тут вообще устроена авторизация? | не отвечает | отвечает |
| Нетипизированный legacy | деградирует | работает так же |
| Монорепа TS + Go + SQL | по серверу на язык, связей между ними нет | сквозной поиск |

Решающая асимметрия: **LSP нужен якорь — символ, который вы уже можете назвать.
Эмбеддинги этот якорь производят.** Отсюда целевой конвейер из трёх ступеней:

```
семантический поиск → находит точку входа
        ↓
LSP → точно обходит граф от неё (кто вызывает, что реализует, где определено)
        ↓
grep → подтверждает по точной строке
```

Ни одна ступень не лишняя, и ни одна не заменяет соседнюю.

Есть и второе соображение, для агента более важное, чем процент попаданий:
**ошибка эмбеддингов дороже ошибки LSP.** Правдоподобный, но нерелевантный фрагмент
уводит модель по ложному следу и сжигает контекст. LSP не бывает неправ — он либо
отвечает точно, либо не отвечает вовсе.

**Практический вывод.** Плагин LSP стоит 5 минут, этот проект — 5 дней. Поэтому
сначала ставим плагин — не как альтернативу, а чтобы снять с семантического индекса
нагрузку, которую он и так несёт хуже. Побочный эффект ценнее основного: **запросы,
на которых LSP спотыкается, и есть готовый golden-набор** для §9. Неделя работы с
включённым LSP-плагином собирает его бесплатно.

### Критерий успеха

Не «работает», а измеримо:

- **Recall@5 ≥ 0.85** на golden-наборе из 40+ реальных запросов (§9).
- Инкрементальная переиндексация после сохранения файла — **< 2 с** до появления в поиске.
- Один вызов `search_code` тратит **< 4000 токенов** контекста вместо ~20 файлов через Read.
- Первичная индексация монорепы (~5k файлов) — **минуты, не часы**.

## 2. Целевое железо и его последствия

Два разных компьютера, и это определяет архитектуру.

| | Машина разработки (эта) | Целевая машина (прод) |
|---|---|---|
| CPU | Intel Core Ultra 9 275HX, 24 ядра | AMD Ryzen AI 9 HX 370 (Strix Point) |
| Ускоритель | **NVIDIA RTX 5060 Mobile 8 GB**, CUDA 13.2 | **AMD XDNA2 NPU, ~50 TOPS** |
| RAM | 61 GB | — |
| Стек инференса | Ollama (CUDA) | ONNX Runtime + Vitis AI EP |

Из этого следует главное архитектурное решение всего проекта:

> **Эмбеддер изолирован за HTTP-контрактом.** TS-ядро никогда не знает, что под ним —
> Ollama на CUDA или Vitis AI на NPU. Переезд между машинами = смена одной строки в конфиге.

Без этого граница размоется, и NPU-специфика протечёт в чанкер и индексатор.

### Что подтверждено про AMD-путь

- `embeddinggemma-300m` **есть** в списке моделей Ryzen AI Software 1.8.0.
- Поддерживаемые платформы: **STX/KRK** (Strix Point, Strix Halo, Krackan Point).
  HX 370 — это Strix Point, попадает. PHX/HPT (Phoenix, Hawk Point) — **не** поддерживаются.
- Развёртывание через ONNX Runtime с Vitis AI Execution Provider; EP сам решает, какие
  части графа уходят на NPU.
- FP32-модели внутренне конвертируются в bfloat16 и компилируются BF16-флоу — вероятный
  маршрут для encoder-only модели.
- С 1.6 Integer Compiler поддерживает A8W8/A16W8 и асимметричную квантизацию, то есть
  готовый квантованный ONNX с HF можно запускать без переобучения.

### Что про модель важно знать заранее

Эти три пункта — источник самых частых тихих провалов качества:

1. **fp16 не поддерживается.** Активации EmbeddingGemma не работают в float16. Только
   fp32, bf16, q8 или q4. Наивное `--fp16` при экспорте в ONNX даст мусор на выходе,
   причём не упадёт, а просто ухудшит вектора.
2. **Префиксы обязательны и асимметричны.**
   - Запрос: `task: search result | query: {текст}`
   - Документ: `title: none | text: {текст}`

   Если проиндексировать с одним префиксом, а искать с другим (или без) — качество
   деградирует молча. Есть также вариант `task: code retrieval | query: ` — кандидат
   на A/B-тест для нашей задачи (§9).
3. **Контекст 2048 токенов**, выход 768 измерений с Matryoshka-усечением до 512/256/128
   (после усечения — обязательная ре-нормализация). 2048 — это жёсткий потолок размера
   чанка вместе с обогащающим заголовком.

### NPU против GPU: честное распределение ролей

Две нагрузки с разной природой:

- **Первичная индексация** — throughput-bound. Десятки тысяч чанков, батчи по 32–64.
  Здесь GPU выигрывает у NPU примерно на порядок.
- **Инкрементальная доиндексация** — latency-bound. Сохранили файл — 3–10 чанков.
  Пропускная способность не нужна вообще; важно, чтобы фоновый процесс не ел батарею
  и не будил дискретную карту. Здесь NPU в своей стихии: единицы ватт.

Отсюда план: `EMBED_BACKEND` выбирается конфигом, и на проде допустимо разное значение
для bulk-джоба и для watch-режима. Заложить в интерфейс сразу, реализовать в Ф5.

## 4. Контракт эмбеддера

Единственная граница между TS-ядром и железом. Оба бэкенда реализуют её байт-в-байт.

```http
POST /embed
Content-Type: application/json

{
  "inputs": ["export function scheduleRedelivery(...)", "..."],
  "kind":   "document" | "query",
  "dims":   768
}
```

```json
{
  "vectors":    [[0.013, -0.221, ...], ...],
  "model":      "embeddinggemma-300m",
  "dims":       768,
  "normalized": true,
  "truncated":  [false, true]
}
```

```http
GET /health
→ { "backend": "ollama"|"npu", "model": "...", "dims": 768,
    "maxTokens": 2048, "ready": true }
```

Правила контракта — намеренно жёсткие, потому что каждое из них закрывает конкретный баг:

- **Префиксы применяет сервис, не клиент.** Префикс — свойство модели. Если его знает
  TS-клиент, то при смене модели забудут поправить, и индекс с поиском разъедутся молча.
  Клиент передаёт только `kind`.
- **Нормализация — на стороне сервиса**, всегда. Потом косинус = скалярное произведение.
- **`truncated`** сообщает, какие входы упёрлись в 2048 токенов. Индексатор это логирует;
  если процент высокий — чанкер плохо режет.
- **`model` возвращается на каждый ответ** и пишется в БД рядом с вектором. Смена модели
  обязана инвалидировать индекс (§5, `model_id`).

### Dev-бэкенд: Ollama

```bash
ollama pull embeddinggemma:300m
```

Обёртка `services/embed-ollama` (Fastify, ~100 строк) навешивает префиксы, режет вход на
батчи и зовёт `POST /api/embed` Ollama. Ollama сам заберёт CUDA на RTX 5060.

### Prod-бэкенд: Ryzen AI NPU  [Ф5]

Python + FastAPI, тот же контракт:

1. Экспорт `google/embeddinggemma-300m` в ONNX (**не fp16** — fp32 или bf16).
   Быстрее взять готовый `onnx-community/embeddinggemma-300m-ONNX`.
2. Квантизация под NPU через Ryzen AI Quantizer (A8W8) либо BF16-флоу.
3. `onnxruntime.InferenceSession(..., providers=["VitisAIExecutionProvider"])`.
4. **Статические шейпы.** NPU не любит динамический `seq_len`. Решение — бакеты длин
   (128 / 256 / 512 / 1024 / 2048): вход паддится до ближайшего бакета, под каждый бакет
   компилируется свой граф. Иначе часть подграфов молча уедет на CPU.
5. **Батчинг обязателен.** Отправлять чанки по одному — накладные расходы на передачу
   в NPU съедят весь выигрыш. Собирать батчи по 32–64.
6. При старте писать в лог, какая доля узлов графа реально ушла на NPU (Vitis AI EP это
   отдаёт). Если там 30% — это провал компиляции, а не «работает медленно».

**Обязательная приёмка Ф5:** прогнать golden-набор (§9) на NPU-бэкенде и сравнить с
эталоном fp32/CUDA. Падение recall@5 больше 3 п.п. — значит квантизация испортила вектора,
и надо поднимать разрядность. Без этой проверки деградация останется незамеченной.

## 5. Схема данных

```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE TABLE repos (
  id              serial PRIMARY KEY,
  name            text NOT NULL UNIQUE,
  root_path       text NOT NULL,
  head_commit     text,
  last_indexed_at timestamptz
);

CREATE TABLE files (
  repo_id    int  NOT NULL REFERENCES repos(id) ON DELETE CASCADE,
  path       text NOT NULL,              -- относительный путь
  blob_sha   text NOT NULL,              -- git blob sha, либо sha256 для untracked
  lang       text NOT NULL,
  indexed_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (repo_id, path)
);

-- Контент-адресуемые чанки: вектор считается один раз на уникальный текст.
CREATE TABLE chunks (
  content_hash bytea PRIMARY KEY,        -- sha256(model_id || embed_text)
  embed_text   text   NOT NULL,          -- что реально ушло в модель
  raw_text     text   NOT NULL,          -- что показываем человеку
  token_count  int    NOT NULL,
  model_id     text   NOT NULL,
  embedding    vector(768) NOT NULL,
  tsv          tsvector GENERATED ALWAYS AS
                 (to_tsvector('simple', embed_text)) STORED
);

CREATE TABLE chunk_locations (
  id           bigserial PRIMARY KEY,
  repo_id      int   NOT NULL REFERENCES repos(id) ON DELETE CASCADE,
  path         text  NOT NULL,
  content_hash bytea NOT NULL REFERENCES chunks(content_hash),
  start_line   int   NOT NULL,
  end_line     int   NOT NULL,
  symbol       text,                     -- scheduleRedelivery
  kind         text,                     -- function | class | method | file_card | preamble
  parent_chain text[],                   -- ['RedeliveryQueue']
  lang         text NOT NULL
);

CREATE INDEX ON chunk_locations (repo_id, path);
CREATE INDEX ON chunk_locations (content_hash);
CREATE INDEX ON chunk_locations USING gin (symbol gin_trgm_ops);

CREATE INDEX chunks_hnsw ON chunks
  USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);
CREATE INDEX chunks_fts  ON chunks USING gin (tsv);
```

### Почему разделены `chunks` и `chunk_locations`

Это не нормализация ради нормализации, а оптимизация под главную боль — **переключение
веток**. Чанк адресуется хэшем своего содержимого. Тогда:

- Файл переименовали → все вектора переиспользуются, меняется только `chunk_locations`.
- `git checkout другая-ветка` → 90% чанков совпадают с уже посчитанными, эмбеддится
  только реальная дельта. Без этого каждый чекаут = переиндексация монорепы.
- Скопипащенная функция в трёх пакетах → один вектор, три локации. Заодно это
  **бесплатный детектор точных дублей**.

`model_id` входит в хэш: смена модели автоматически создаёт новое пространство хэшей и
не смешивает несравнимые вектора.

### Оценка объёма

Монорепа ~5000 файлов TS → ориентировочно 40–60k чанков.

| | размер |
|---|---|
| Вектора `vector(768)` fp32 | ~123 МБ |
| Они же `halfvec(768)` | ~61 МБ |
| Текст чанков (raw + embed) | ~200–400 МБ |
| HNSW-индекс | ~150–250 МБ |

Если HNSW-индекс перестанет влезать в `shared_buffers` — перейти на
`halfvec(768)` + `halfvec_cosine_ops`. Потеря точности на retrieval пренебрежима,
память вдвое меньше. Пока не мерили — не оптимизируем.

## 6. Чанкинг — 80% результата

> Резать по 500 символов — получите мусор. Резать по AST — получите работающий поиск.
> Это основная часть работы, и она не про ИИ.

Если в проекте будет одно место, куда стоит вложить время — это здесь.

### Извлекаемые узлы (TypeScript / JavaScript)

Через `tree-sitter` с грамматиками `tree-sitter-typescript` / `tree-sitter-tsx`:

| Узел AST | Что даёт |
|---|---|
| `function_declaration` | обычные функции |
| `method_definition` | методы классов |
| `class_declaration` | класс целиком, если влезает; иначе — по методам |
| `lexical_declaration` → `arrow_function` | `const foo = () => {}` |
| `interface_declaration`, `type_alias_declaration`, `enum_declaration` | типы — важны для «а какая структура у заказа» |
| `export_statement` | разворачивается до вложенного узла, но помечает символ как экспортируемый |

Для React отдельно: компонент — это `arrow_function`/`function_declaration`, чьё имя
с заглавной буквы и который возвращает JSX. Помечать `kind: 'component'` — это заметно
помогает запросам вида «где рисуется форма оплаты».

### Бюджеты размеров

Потолок модели — 2048 токенов, заголовок обогащения съедает ~120.

```
MIN_TOKENS    = 40     ниже — сливаем с соседями
TARGET_TOKENS = 300
MAX_TOKENS    = 700    выше — режем
HEADER_BUDGET = 120
```

Три правила:

- **Узел > MAX** → режем по верхнеуровневым выражениям тела. Каждая часть получает
  заголовок с сигнатурой родителя и пометкой `(part k/n)`. Функция на 800 строк не
  должна давать один бессмысленный вектор.
- **Узел < MIN** → жадно объединяем с соседними братьями того же родителя, пока не
  дойдём до TARGET. Двадцать однострочных экспортов из `index.ts` — это один чанк,
  а не двадцать бесполезных.
- **Всё непокрытое** (импорты, константы верхнего уровня, side-effect код) → чанк
  `kind: 'preamble'`.

### Обогащающий заголовок

Ключевой приём. Добавляется в `embed_text`, но **не** в `raw_text` (человеку показываем
чистый код).

```
// repo: acme-monorepo
// file: packages/queue/src/backoff.ts
// path-words: packages queue src backoff
// exports: scheduleRedelivery, BackoffPolicy
// imports: ./types, p-retry, ../payments/gateway
// scope: class RedeliveryQueue > method scheduleRedelivery
// doc: Schedules a failed payment for another delivery attempt with exponential backoff.
```

Зачем каждая строка:

- `path-words` — разбитый на слова путь. Именно это позволяет запросу
  «payment retry» зацепиться за `src/lib/queue/backoff.ts` через названия каталогов,
  даже когда в теле функции слова `payment` нет.
- `imports` — соседи по графу зависимостей. `../payments/gateway` в импортах говорит
  о назначении модуля больше, чем его собственный код.
- `scope` — родительская цепочка. Метод `execute()` сам по себе не значит ничего;
  `class RedeliveryQueue > method execute` значит.
- `doc` — первая строка JSDoc. Комментарии пишутся человеческим языком, ровно тем,
  которым формулируется запрос. Самый дешёвый источник семантики в файле.

### Карточка файла

Дополнительно на каждый файл — один чанк `kind: 'file_card'`: путь, список экспортов,
верхний JSDoc, импорты, без тел функций. Он отвечает на запросы уровня «какие модули
вообще про платежи», на которые чанк-функция ответить не может.

### Что не индексируем

Deny-list — одновременно про качество и про безопасность:

```
.env*, *.pem, *.key, *.p12, *.pfx, credentials*, secrets/**, id_rsa*
node_modules/**, dist/**, build/**, .next/**, out/**, coverage/**, .turbo/**
*.lock, package-lock.json, pnpm-lock.yaml, yarn.lock
*.min.js, *.map, vendor/**, __generated__/**, *.pb.go, *.d.ts (генерённые)
```

Плюс эвристики: файл > 1 МБ; наличие нулевого байта (бинарник); средняя длина строки
> 200 символов (минифицировано); отсутствие пути в `git ls-files` при
`respect_gitignore: true`.

Секреты в векторной базе — это секреты, которые уедут в контекст облачной модели при
первом же релевантном запросе. Deny-list должен быть строгим по умолчанию.

## 7. Инкрементальность

### Полный проход (первичный)

1. `git ls-files -s` → список `<mode> <blob_sha> <stage>\t<path>`.
2. Фильтрация по deny-list и языкам.
3. Пул воркеров (`os.cpus().length - 2`) читает и чанкует файлы.
4. Батчи по 64 чанка → `POST /embed`.
5. Upsert в `chunks` (`ON CONFLICT (content_hash) DO NOTHING`), затем `chunk_locations`.

### Дешёвый диф

`git ls-files -s` отдаёт **blob sha по каждому файлу без чтения самих файлов**. Одна
команда даёт полное состояние рабочего дерева. Сравнение с `files.blob_sha` в БД
находит изменённое множество за миллисекунды даже на монорепе.

Это делает переключение веток дешёвой операцией, а не катастрофой:

```
.git/HEAD изменился
  → git ls-files -s
  → диф с files
  → перечанковать только различающиеся пути
  → из их чанков посчитать только те content_hash, которых ещё нет в chunks
```

На типичном чекауте между ветками реально эмбеддится несколько десятков чанков.

### Watch-режим

- `chokidar` на корень репозитория, `ignoreInitial: true`,
  `awaitWriteFinish: { stabilityThreshold: 300 }` — иначе поймаем частично записанный
  файл от сборщика.
- Отдельно `.git/HEAD` и `.git/index` — чекауты, ребейзы, `git stash`.
- Debounce 1500 мс, накопление в `Set<path>` (дедуп: сборщики трогают один файл по
  многу раз).
- Очередь с backpressure: если в буфере > 500 путей — переключиться на полный
  `git ls-files -s`-диф, это дешевле поштучной обработки.

### Обработка одного файла

```
blob_sha изменился?  нет → выход
  ├─ файл удалён → DELETE chunk_locations WHERE repo_id, path; DELETE files
  └─ файл изменён:
       чанкуем → считаем content_hash для каждого чанка
       SELECT content_hash FROM chunks WHERE content_hash = ANY($1)
       эмбеддим только недостающие
       BEGIN
         INSERT INTO chunks ... ON CONFLICT DO NOTHING
         DELETE FROM chunk_locations WHERE repo_id=$1 AND path=$2
         INSERT INTO chunk_locations ...
         UPDATE files SET blob_sha, indexed_at
       COMMIT
```

Замена локаций целиком для файла — вместо попыток вычислить дельту по строкам. Проще,
атомарнее, и стоит копейки.

### Сборка мусора

Раз в час, вне пиковой нагрузки:

```sql
DELETE FROM chunks c
 WHERE NOT EXISTS (SELECT 1 FROM chunk_locations l
                    WHERE l.content_hash = c.content_hash);
```

## 8. Поиск и ранжирование

Чисто векторный поиск по коду **недостаточен**. Он проваливается ровно там, где
запрос содержит точное имя символа — а такие запросы Claude задаёт постоянно. Нужен
гибрид с самого начала.

### Пайплайн

```
запрос
 ├─ вектор: embed(kind=query) → HNSW top-50
 └─ лексика: to_tsquery + trigram по symbol → top-50
        ↓
   RRF-слияние (k=60)
        ↓
   MMR-диверсификация: не более 2 чанков из одного файла
        ↓
   [Ф6] cross-encoder реранк top-30 → top-8
        ↓
   top-8 с обрезкой по токен-бюджету
```

**RRF** (Reciprocal Rank Fusion) выбран вместо взвешенной суммы скоров сознательно:
косинусная близость и `ts_rank` живут в несопоставимых шкалах, а подбор весов между
ними — бесконечная возня. RRF работает по рангам и не требует калибровки.

```sql
WITH vec AS (
  SELECT l.id, ROW_NUMBER() OVER (ORDER BY c.embedding <=> $1) AS rank
    FROM chunk_locations l JOIN chunks c USING (content_hash)
   WHERE l.repo_id = $2
   ORDER BY c.embedding <=> $1
   LIMIT 50
),
lex AS (
  SELECT l.id, ROW_NUMBER() OVER (ORDER BY ts_rank(c.tsv, q) DESC) AS rank
    FROM chunk_locations l JOIN chunks c USING (content_hash),
         plainto_tsquery('simple', $3) q
   WHERE l.repo_id = $2 AND c.tsv @@ q
   ORDER BY ts_rank(c.tsv, q) DESC
   LIMIT 50
)
SELECT id, SUM(1.0 / (60 + rank)) AS score
  FROM (SELECT * FROM vec UNION ALL SELECT * FROM lex) u
 GROUP BY id
 ORDER BY score DESC
 LIMIT 20;
```

### Токенизация идентификаторов

`scheduleRedelivery` для `to_tsvector('simple', ...)` — один токен, и запрос
`redelivery` его не найдёт. Нужна предобработка `embed_text` перед FTS: разбить
camelCase / snake_case / kebab-case и **дописать** развёрнутые слова к тексту, сохранив
исходные идентификаторы.

`scheduleRedelivery` → `scheduleRedelivery schedule redelivery`

Реализовать как SQL-функцию `code_tokens(text)` и использовать её в generated-колонке
`tsv` (миграция `002_fts.sql`). Без этого лексическая половина гибрида работает вполсилы.

### Диверсификация

Без неё топ-5 регулярно оказывается пятью соседними чанками одного файла — контекст
потрачен, а обзора нет. Жёсткое правило: максимум 2 чанка на файл в выдаче, плюс, по
возможности, минимум 3 разных файла.

## 9. Оценка качества

Раздел, который обычно пропускают, — и потом полгода «улучшают» поиск наугад.

### Golden-набор

`src/eval/golden.jsonl`, **минимум 40 записей**, собранных из реальных вопросов:

```jsonl
{"q": "где обрабатывается повторная отправка платежа",
 "expect": ["packages/queue/src/backoff.ts::scheduleRedelivery"]}
{"q": "как формируется JWT для сервис-сервис вызовов",
 "expect": ["packages/auth/src/tokens.ts::signInternal"]}
{"q": "валидация телефона при регистрации",
 "expect": ["apps/web/src/forms/signup.ts::phoneRule",
            "packages/validators/src/phone.ts::isE164"]}
```

Правило составления: **формулировать запрос так, как его задал бы человек, не знающий
кодовой базы**, и намеренно не использовать слова из имени искомого символа. Иначе
измеряется grep, а не семантика.

**Откуда брать записи.** Не выдумывать за столом. Включить LSP-плагин (§1) и неделю
работать как обычно, записывая каждый вопрос, на который LSP и grep не ответили за
разумное время. Это ровно то множество, ради которого строится индекс, — и потому
единственный честный набор для его оценки. Выдуманные запросы систематически смещены
в сторону того, что мы уже умеем находить.

### Метрики

- `recall@5` — целевая, попал ли ожидаемый символ в топ-5.
- `MRR@10` — чувствительна к позиции, ловит мелкие регрессии ранжирования.
- `p50 / p95` латентности поиска.
- % чанков с `truncated: true` — здоровье чанкера.

`npm run eval` печатает таблицу и дифф к предыдущему прогону. Гоняется на каждое
изменение чанкера, префиксов, весов или модели.

### Что проверить экспериментами

Порядок по ожидаемой отдаче:

1. `task: search result | query: ` **против** `task: code retrieval | query: ` для
   запросов. Второй вариант обучен под наш кейс — вероятный лёгкий выигрыш.
2. Обогащающий заголовок целиком vs без `path-words` vs без `imports`. Проверить, что
   каждая строка заголовка окупается, а не разбавляет вектор.
3. TARGET_TOKENS 200 / 300 / 500.
4. Гибрид vs чистый вектор — зафиксировать реальный вклад лексической половины.
5. Matryoshka 768 vs 512 vs 256. Если 256 не роняет recall — вчетверо меньше памяти
   и быстрее HNSW.

## 10. MCP-сервер

Транспорт stdio, `@modelcontextprotocol/sdk`. Регистрация в `.mcp.json` проекта.

### Инструменты

Один `search_code` — недостаточно: модель регулярно нуждается в уточнении контекста
и в понимании структуры проекта.

**1. `search_code`** — основной.
```ts
{ query: string, k?: number = 8, repo?: string, path_glob?: string,
  lang?: string, mode?: 'hybrid' | 'semantic' | 'lexical' }
```

**2. `find_similar_code`** — смысловые дубли, второй ключевой сценарий.
```ts
{ path: string, symbol?: string, line?: number,
  k?: number = 8, exclude_same_file?: boolean = true }
```
Реализация: берём вектор исходного чанка, ищем ближайшие, исключаем сам чанк.
Точные копии находятся бесплатно — по совпадению `content_hash`.

**3. `expand_context`** — приблизить, если найденный фрагмент оказался коротким.
```ts
{ path: string, start_line: number, end_line: number,
  before?: number = 20, after?: number = 20 }
```
Существует ровно затем, чтобы модель не читала файл целиком ради двадцати строк.

**4. `repo_map`** — структура и экспорты, для ориентации в незнакомом проекте.
```ts
{ repo?: string, path_prefix?: string, depth?: number = 2 }
```

**5. `index_status`** — сколько файлов и чанков, лаг очереди, модель, время последней
индексации. Нужен, чтобы отличить «в коде такого нет» от «индекс отстал на 200 файлов».

### Формат выдачи

Компактный текст, не JSON-простыня. Каждый лишний токен здесь — токен, отнятый у работы.

```
1. packages/queue/src/backoff.ts:47-89  ·  scheduleRedelivery  ·  0.89
   class RedeliveryQueue > method scheduleRedelivery
   > Schedules a failed payment for another delivery attempt with exponential backoff.
   export async function scheduleRedelivery(payment: Payment, attempt: number) {
     const delay = Math.min(BASE_DELAY * 2 ** attempt, MAX_DELAY)
     ...

2. packages/payments/src/gateway.ts:203-231  ·  handleWebhookFailure  ·  0.74
   ...
```

Жёсткие правила формата:

- Хедер строки — всегда `path:start-end`. Это кликабельно в терминале и сразу годится
  для `Read`.
- Тело — максимум 15 строк на попадание, с обрезкой посередине для длинных.
- Общий бюджет ответа — **4000 токенов**, режем по мере набора.
- В конце — подсказка: `используйте expand_context для полного тела`.

### Описания инструментов

Описание — это промпт, по которому модель решает, звать ли инструмент. Формулировать
явно и с указанием границ:

> `search_code` — найти код по смыслу описания, а не по точному имени. Используйте,
> когда не знаете, как называется искомая функция или файл: «где обрабатывается
> повторная отправка платежа», «как реализована инвалидация кеша». Для поиска по
> известному имени символа используйте Grep — он быстрее и точнее.

Последнее предложение важно: без него модель начнёт звать семантический поиск вместо
grep там, где grep лучше.

### Регистрация

```json
{
  "mcpServers": {
    "code-search": {
      "command": "node",
      "args": ["/opt/scs/dist/bin/scs-mcp.js"],
      "env": { "SCS_REPO": "acme-monorepo", "SCS_PG": "postgres://scs@localhost/scs" }
    }
  }

```

| **Ф3** | MCP-сервер, 5 инструментов, форматирование, токен-бюджет, `.mcp.json` | 1–2 дня | Claude Code сам зовёт `search_code` и получает 5 точных фрагментов |

| **Ф6** | cross-encoder реранкер, мульти-репо поиск, `find_similar_code` в проде | по потребности | recall@5 ≥ 0.85 |

**Точка «дальше можно не делать»** — конец Ф3. Уже там инструмент приносит основную
пользу, просто без автообновления индекса (`scs index` руками). Ф4 превращает это в
удобство, Ф5 — в энергоэффективность на целевой машине.

**Ф−1 идёт параллельно, а не последовательно** — она ничего не блокирует, кроме Ф2.
Ставим плагин сегодня и спокойно начинаем Ф0/Ф1: к моменту, когда понадобится мерить,
golden-набор уже накопится сам.

Порядок не переставлять: Ф2 (измерение) стоит раньше Ф3 (интеграция) намеренно.
Интегрировать в Claude Code поиск, качество которого не измерено, — значит потом гадать,
где именно всё сломалось.

## 13. Риски

| Риск | Вероятность | Последствие | Что делаем |
|---|---|---|---|
| Квантизация под NPU роняет качество векторов | средняя | тихая деградация поиска | golden-набор на fp32/CUDA как эталон; порог −3 п.п. recall@5; при провале — bf16 вместо A8W8 |
| Часть графа не компилируется на NPU, уходит на CPU | средняя | нет выигрыша по энергии | логировать долю узлов на NPU при старте; статические шейпы через бакеты длин |
| Экспорт в fp16 «работает», но портит вектора | **высокая** | молчаливая деградация | запрет fp16 в коде экспорта + assert на косинус к эталонным векторам |
| Рассинхрон префиксов индекс/запрос | **высокая** | recall падает в разы | префиксы только внутри сервиса, `kind` в контракте, тест на асимметрию |
| Чанки упираются в 2048 токенов | средняя | обрезанный смысл | поле `truncated` в ответе, алерт при доле > 5% |
| Ветки переключаются часто, индекс не успевает | низкая | лаг поиска | контент-адресуемость (§5) + `git ls-files -s` диф |
| Модель слабо понимает код на не-JS языках | средняя | плохой поиск в монорепе | eval по языкам отдельно; при провале — `jina-embeddings-v2-base-code` или `Qwen3-Embedding-0.6B` |
| HNSW не влезает в память | низкая | медленный поиск | `halfvec(768)`; Matryoshka до 256 |
| tree-sitter грамматики ломаются при обновлении | низкая | падение чанкера | пин версий грамматик, снапшот-тесты чанкера на фикстурах |
| Семантический поиск зовётся там, где точнее LSP или grep | средняя | ложные следы, сожжённый контекст | явные границы в описаниях инструментов (§10); LSP-плагин включён параллельно |

## 14. Открытые вопросы

1. **Реранкер в Ф6** — `bge-reranker-v2-m3` или `Qwen3-Reranker-0.6B`? Решать по данным
   Ф2: если recall@20 сильно выше recall@5, реранкер окупится; если они близки — проблема
   в кандидатах, а не в ранжировании, и реранкер не поможет.
2. **Резервная модель** — если EmbeddingGemma слабо возьмёт код, кандидаты:
   `jina-embeddings-v2-base-code` (161M, контекст 8192, заточена под код) и
   `Qwen3-Embedding-0.6B` (контекст 32k, сильные результаты на MTEB-Code). Обе потребуют
   самостоятельного экспорта в ONNX под Vitis AI — в отличие от EmbeddingGemma,
   поддержанной AMD официально. Это и есть главный аргумент за EmbeddingGemma на старте.
3. **Мульти-репо в MCP** — искать по всем зарегистрированным репозиториям сразу или
   только по текущему? Предложение: по умолчанию текущий, параметр `repo: "*"` для
   кросс-репо поиска дублей.
4. **Индексация истории git** — искать по удалённому коду («а где это было до рефакторинга»)
   технически возможно, но кратно раздувает индекс. Отложено.
