# Семантический поиск по коду: локальный демон + MCP

Технический документ реализации. Версия 1, 2026-08-06.

---

## 1. Задача

Дать Claude Code инструмент поиска **по смыслу**, а не по строке.

Два сценария, ради которых всё затевается:

1. **«Где обрабатывается повторная отправка платежа?»** — grep по `retry` даёт двести
   совпадений, grep по `payment` — тысячу, а нужная логика лежит в
   `src/lib/queue/backoff.ts::scheduleRedelivery`. Слово не угадать.
2. **«Где ещё в монорепе делается то же самое?»** — три реализации одной логики,
   названные по-разному. Grep их не покажет принципиально.

**Не является заменой grep.** Точный поиск по имени символа grep делает лучше и быстрее.
Рабочая схема — гибрид: семантический поиск сужает область до 5–8 мест, дальше точный
поиск и чтение внутри неё.

### Отношение к LSP: дополнение, а не конкурент

У Claude Code есть официальные плагины code intelligence на базе LSP
(`/plugin install typescript-lsp@claude-plugins-official`) — девять операций, включая
переход к определению, поиск ссылок, реализации и call hierarchy.

Соблазнительно считать их «худшей версией» семантического поиска. Это не так: они
отвечают на другой класс вопросов, и разница не в качестве, а в природе гарантий.
**LSP точен и полон над графом типов; эмбеддинги приблизительны и полноты не гарантируют.**

| Вопрос | LSP | Эмбеддинги |
|---|---|---|
| Кто вызывает `scheduleRedelivery`? | **все** вызовы, гарантированно | 5 похожих, без гарантии полноты |
| Что сломается при смене сигнатуры? | точный ответ | не отвечает |
| Где определён символ? | одна точка | приблизительно |
| Где обрабатывается повторная отправка платежа? *(имени не знаю)* | **не отвечает** — нужен символ | ядро задачи |
| Где ещё делается то же самое? *(названо иначе)* | **слеп** | ядро задачи |
| Как тут вообще устроена авторизация? | не отвечает | отвечает |
| Нетипизированный legacy | деградирует | работает так же |
| Монорепа TS + Go + SQL | по серверу на язык, связей между ними нет | сквозной поиск |

Решающая асимметрия: **LSP нужен якорь — символ, который вы уже можете назвать.
Эмбеддинги этот якорь производят.** Отсюда целевой конвейер из трёх ступеней:

```
семантический поиск → находит точку входа
        ↓
LSP → точно обходит граф от неё (кто вызывает, что реализует, где определено)
        ↓
grep → подтверждает по точной строке
```

Ни одна ступень не лишняя, и ни одна не заменяет соседнюю.

Есть и второе соображение, для агента более важное, чем процент попаданий:
**ошибка эмбеддингов дороже ошибки LSP.** Правдоподобный, но нерелевантный фрагмент
уводит модель по ложному следу и сжигает контекст. LSP не бывает неправ — он либо
отвечает точно, либо не отвечает вовсе.

**Практический вывод.** Плагин LSP стоит 5 минут, этот проект — 5 дней. Поэтому
сначала ставим плагин — не как альтернативу, а чтобы снять с семантического индекса
нагрузку, которую он и так несёт хуже. Побочный эффект ценнее основного: **запросы,
на которых LSP спотыкается, и есть готовый golden-набор** для §9. Неделя работы с
включённым LSP-плагином собирает его бесплатно.

### Критерий успеха

Не «работает», а измеримо:

- **Recall@5 ≥ 0.85** на golden-наборе из 40+ реальных запросов (§9).
  На сегодня **не достигнут**: 37.9% на наборе из транскриптов (§17). На
  самодельных наборах достигался, но они измеряли не то.
- Инкрементальная переиндексация после сохранения файла — **< 2 с** до появления в поиске.
- Один вызов `search_code` тратит **< 4000 токенов** контекста вместо ~20 файлов через Read.
- Первичная индексация монорепы (~5k файлов) — **минуты, не часы**.

## 2. Целевое железо и его последствия

Два разных компьютера, и это определяет архитектуру.

| | Машина разработки (эта) | Целевая машина (прод) |
|---|---|---|
| CPU | Intel Core Ultra 9 275HX, 24 ядра | AMD Ryzen AI 9 HX 370 (Strix Point) |
| Ускоритель | **NVIDIA RTX 5060 Mobile 8 GB**, CUDA 13.2 | **AMD XDNA2 NPU, ~50 TOPS** |
| RAM | 61 GB | — |
| Стек инференса | Ollama (CUDA) | ONNX Runtime + Vitis AI EP |

Из этого следует главное архитектурное решение всего проекта:

> **Эмбеддер изолирован за HTTP-контрактом.** TS-ядро никогда не знает, что под ним —
> Ollama на CUDA или Vitis AI на NPU. Переезд между машинами = смена одной строки в конфиге.

Без этого граница размоется, и NPU-специфика протечёт в чанкер и индексатор.

### Что подтверждено про AMD-путь

- `embeddinggemma-300m` **есть** в списке моделей Ryzen AI Software 1.8.0.
- Поддерживаемые платформы: **STX/KRK** (Strix Point, Strix Halo, Krackan Point).
  HX 370 — это Strix Point, попадает. PHX/HPT (Phoenix, Hawk Point) — **не** поддерживаются.
- Развёртывание через ONNX Runtime с Vitis AI Execution Provider; EP сам решает, какие
  части графа уходят на NPU.
- FP32-модели внутренне конвертируются в bfloat16 и компилируются BF16-флоу — вероятный
  маршрут для encoder-only модели.
- С 1.6 Integer Compiler поддерживает A8W8/A16W8 и асимметричную квантизацию, то есть
  готовый квантованный ONNX с HF можно запускать без переобучения.

### Что про модель важно знать заранее

Эти три пункта — источник самых частых тихих провалов качества:

1. **fp16 не поддерживается.** Активации EmbeddingGemma не работают в float16. Только
   fp32, bf16, q8 или q4. Наивное `--fp16` при экспорте в ONNX даст мусор на выходе,
   причём не упадёт, а просто ухудшит вектора.
2. **Префиксы обязательны и асимметричны.**
   - Запрос: `task: search result | query: {текст}`
   - Документ: `title: none | text: {текст}`

   Если проиндексировать с одним префиксом, а искать с другим (или без) — качество
   деградирует молча. Есть также вариант `task: code retrieval | query: ` — кандидат
   на A/B-тест для нашей задачи (§9).
3. **Контекст 2048 токенов**, выход 768 измерений с Matryoshka-усечением до 512/256/128
   (после усечения — обязательная ре-нормализация). 2048 — это жёсткий потолок размера
   чанка вместе с обогащающим заголовком.

### NPU против GPU: честное распределение ролей

Две нагрузки с разной природой:

- **Первичная индексация** — throughput-bound. Десятки тысяч чанков, батчи по 32–64.
  Здесь GPU выигрывает у NPU примерно на порядок.
- **Инкрементальная доиндексация** — latency-bound. Сохранили файл — 3–10 чанков.
  Пропускная способность не нужна вообще; важно, чтобы фоновый процесс не ел батарею
  и не будил дискретную карту. Здесь NPU в своей стихии: единицы ватт.

Отсюда план: `EMBED_BACKEND` выбирается конфигом, и на проде допустимо разное значение
для bulk-джоба и для watch-режима. Заложить в интерфейс сразу, реализовать в Ф7.

## 4. Контракт эмбеддера

Единственная граница между TS-ядром и железом. Оба бэкенда реализуют её байт-в-байт.

```http
POST /embed
Content-Type: application/json

{
  "inputs": ["export function scheduleRedelivery(...)", "..."],
  "kind":   "document" | "query",
  "dims":   768
}
```

```json
{
  "vectors":    [[0.013, -0.221, ...], ...],
  "model":      "embeddinggemma-300m",
  "dims":       768,
  "normalized": true,
  "truncated":  [false, true]
}
```

```http
GET /health
→ { "backend": "ollama"|"npu", "model": "...", "dims": 768,
    "maxTokens": 2048, "ready": true }
```

Правила контракта — намеренно жёсткие, потому что каждое из них закрывает конкретный баг:

- **Префиксы применяет сервис, не клиент.** Префикс — свойство модели. Если его знает
  TS-клиент, то при смене модели забудут поправить, и индекс с поиском разъедутся молча.
  Клиент передаёт только `kind`.
- **Нормализация — на стороне сервиса**, всегда. Потом косинус = скалярное произведение.
- **`truncated`** сообщает, какие входы упёрлись в 2048 токенов. Индексатор это логирует;
  если процент высокий — чанкер плохо режет.
- **`model` возвращается на каждый ответ** и пишется в БД рядом с вектором. Смена модели
  обязана инвалидировать индекс (§5, `model_id`).

### Dev-бэкенд: Ollama

```bash
ollama pull embeddinggemma:300m
```

Обёртка `services/embed-ollama` (Fastify, ~100 строк) навешивает префиксы, режет вход на
батчи и зовёт `POST /api/embed` Ollama. Ollama сам заберёт CUDA на RTX 5060.

### Prod-бэкенд: Ryzen AI NPU  [Ф7]

Python + FastAPI, тот же контракт:

1. Экспорт `google/embeddinggemma-300m` в ONNX (**не fp16** — fp32 или bf16).
   Быстрее взять готовый `onnx-community/embeddinggemma-300m-ONNX`.
2. Квантизация под NPU через Ryzen AI Quantizer (A8W8) либо BF16-флоу.
3. `onnxruntime.InferenceSession(..., providers=["VitisAIExecutionProvider"])`.
4. **Статические шейпы.** NPU не любит динамический `seq_len`. Решение — бакеты длин
   (128 / 256 / 512 / 1024 / 2048): вход паддится до ближайшего бакета, под каждый бакет
   компилируется свой граф. Иначе часть подграфов молча уедет на CPU.
5. **Батчинг обязателен.** Отправлять чанки по одному — накладные расходы на передачу
   в NPU съедят весь выигрыш. Собирать батчи по 32–64.
6. При старте писать в лог, какая доля узлов графа реально ушла на NPU (Vitis AI EP это
   отдаёт). Если там 30% — это провал компиляции, а не «работает медленно».

**Обязательная приёмка Ф7:** прогнать golden-набор (§9) на NPU-бэкенде и сравнить с
эталоном fp32/CUDA. Падение recall@5 больше 3 п.п. — значит квантизация испортила вектора,
и надо поднимать разрядность. Без этой проверки деградация останется незамеченной.

## 5. Схема данных

```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE TABLE repos (
  id              serial PRIMARY KEY,
  name            text NOT NULL UNIQUE,
  root_path       text NOT NULL,
  head_commit     text,
  last_indexed_at timestamptz
);

CREATE TABLE files (
  repo_id    int  NOT NULL REFERENCES repos(id) ON DELETE CASCADE,
  path       text NOT NULL,              -- относительный путь
  blob_sha   text NOT NULL,              -- git blob sha, либо sha256 для untracked
  lang       text NOT NULL,
  indexed_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (repo_id, path)
);

-- Контент-адресуемые чанки: вектор считается один раз на уникальный текст.
CREATE TABLE chunks (
  content_hash bytea PRIMARY KEY,        -- sha256(model_id || embed_text)
  embed_text   text   NOT NULL,          -- что реально ушло в модель
  raw_text     text   NOT NULL,          -- что показываем человеку
  token_count  int    NOT NULL,
  model_id     text   NOT NULL,
  embedding    vector(768) NOT NULL,
  tsv          tsvector GENERATED ALWAYS AS
                 (to_tsvector('simple', embed_text)) STORED
);

CREATE TABLE chunk_locations (
  id           bigserial PRIMARY KEY,
  repo_id      int   NOT NULL REFERENCES repos(id) ON DELETE CASCADE,
  path         text  NOT NULL,
  content_hash bytea NOT NULL REFERENCES chunks(content_hash),
  start_line   int   NOT NULL,
  end_line     int   NOT NULL,
  symbol       text,                     -- scheduleRedelivery
  kind         text,                     -- function | class | method | file_card | preamble
  parent_chain text[],                   -- ['RedeliveryQueue']
  lang         text NOT NULL
);

CREATE INDEX ON chunk_locations (repo_id, path);
CREATE INDEX ON chunk_locations (content_hash);
CREATE INDEX ON chunk_locations USING gin (symbol gin_trgm_ops);

CREATE INDEX chunks_hnsw ON chunks
  USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);
CREATE INDEX chunks_fts  ON chunks USING gin (tsv);
```

### Почему разделены `chunks` и `chunk_locations`

Это не нормализация ради нормализации, а оптимизация под главную боль — **переключение
веток**. Чанк адресуется хэшем своего содержимого. Тогда:

- Файл переименовали → все вектора переиспользуются, меняется только `chunk_locations`.
- `git checkout другая-ветка` → 90% чанков совпадают с уже посчитанными, эмбеддится
  только реальная дельта. Без этого каждый чекаут = переиндексация монорепы.
- Скопипащенная функция в трёх пакетах → один вектор, три локации. Заодно это
  **бесплатный детектор точных дублей**.

`model_id` входит в хэш: смена модели автоматически создаёт новое пространство хэшей и
не смешивает несравнимые вектора.

### Оценка объёма

Монорепа ~5000 файлов TS → ориентировочно 40–60k чанков.

| | размер |
|---|---|
| Вектора `vector(768)` fp32 | ~123 МБ |
| Они же `halfvec(768)` | ~61 МБ |
| Текст чанков (raw + embed) | ~200–400 МБ |
| HNSW-индекс | ~150–250 МБ |

Если HNSW-индекс перестанет влезать в `shared_buffers` — перейти на
`halfvec(768)` + `halfvec_cosine_ops`. Потеря точности на retrieval пренебрежима,
память вдвое меньше. Пока не мерили — не оптимизируем.

## 6. Чанкинг — 80% результата

> Резать по 500 символов — получите мусор. Резать по AST — получите работающий поиск.
> Это основная часть работы, и она не про ИИ.

Если в проекте будет одно место, куда стоит вложить время — это здесь.

### Извлекаемые узлы (TypeScript / JavaScript)

Через `tree-sitter` с грамматиками `tree-sitter-typescript` / `tree-sitter-tsx`:

| Узел AST | Что даёт |
|---|---|
| `function_declaration` | обычные функции |
| `method_definition` | методы классов |
| `class_declaration` | класс целиком, если влезает; иначе — по методам |
| `lexical_declaration` → `arrow_function` | `const foo = () => {}` |
| `interface_declaration`, `type_alias_declaration`, `enum_declaration` | типы — важны для «а какая структура у заказа» |
| `export_statement` | разворачивается до вложенного узла, но помечает символ как экспортируемый |

Для React отдельно: компонент — это `arrow_function`/`function_declaration`, чьё имя
с заглавной буквы и который возвращает JSX. Помечать `kind: 'component'` — это заметно
помогает запросам вида «где рисуется форма оплаты».

### Бюджеты размеров

Потолок модели — 2048 токенов, заголовок обогащения съедает ~120.

```
MIN_TOKENS    = 40     ниже — сливаем с соседями
TARGET_TOKENS = 300
MAX_TOKENS    = 700    выше — режем
HEADER_BUDGET = 120
```

Три правила:

- **Узел > MAX** → режем по верхнеуровневым выражениям тела. Каждая часть получает
  заголовок с сигнатурой родителя и пометкой `(part k/n)`. Функция на 800 строк не
  должна давать один бессмысленный вектор.
- **Узел < MIN** → жадно объединяем с соседними братьями того же родителя, пока не
  дойдём до TARGET. Двадцать однострочных экспортов из `index.ts` — это один чанк,
  а не двадцать бесполезных.
- **Всё непокрытое** (импорты, константы верхнего уровня, side-effect код) → чанк
  `kind: 'preamble'`.

### Обогащающий заголовок

Ключевой приём. Добавляется в `embed_text`, но **не** в `raw_text` (человеку показываем
чистый код).

```
// repo: acme-monorepo
// file: packages/queue/src/backoff.ts
// path-words: packages queue src backoff
// exports: scheduleRedelivery, BackoffPolicy
// imports: ./types, p-retry, ../payments/gateway
// scope: class RedeliveryQueue > method scheduleRedelivery
// doc: Schedules a failed payment for another delivery attempt with exponential backoff.
```

Зачем каждая строка:

- `path-words` — разбитый на слова путь. Именно это позволяет запросу
  «payment retry» зацепиться за `src/lib/queue/backoff.ts` через названия каталогов,
  даже когда в теле функции слова `payment` нет.
- `imports` — соседи по графу зависимостей. `../payments/gateway` в импортах говорит
  о назначении модуля больше, чем его собственный код.
- `scope` — родительская цепочка. Метод `execute()` сам по себе не значит ничего;
  `class RedeliveryQueue > method execute` значит.
- `doc` — первая строка JSDoc. Комментарии пишутся человеческим языком, ровно тем,
  которым формулируется запрос. Самый дешёвый источник семантики в файле.

### Карточка файла

Дополнительно на каждый файл — один чанк `kind: 'file_card'`: путь, список экспортов,
верхний JSDoc, импорты, без тел функций. Он отвечает на запросы уровня «какие модули
вообще про платежи», на которые чанк-функция ответить не может.

### Что не индексируем

Deny-list — одновременно про качество и про безопасность:

```
.env*, *.pem, *.key, *.p12, *.pfx, credentials*, secrets/**, id_rsa*
node_modules/**, dist/**, build/**, .next/**, out/**, coverage/**, .turbo/**
*.lock, package-lock.json, pnpm-lock.yaml, yarn.lock
*.min.js, *.map, vendor/**, __generated__/**, *.pb.go, *.d.ts (генерённые)
```

Плюс эвристики: файл > 1 МБ; наличие нулевого байта (бинарник); средняя длина строки
> 200 символов (минифицировано); отсутствие пути в `git ls-files` при
`respect_gitignore: true`.

Секреты в векторной базе — это секреты, которые уедут в контекст облачной модели при
первом же релевантном запросе. Deny-list должен быть строгим по умолчанию.

## 7. Инкрементальность

### Полный проход (первичный)

1. `git ls-files -s` → список `<mode> <blob_sha> <stage>\t<path>`.
2. Фильтрация по deny-list и языкам.
3. Пул воркеров (`os.cpus().length - 2`) читает и чанкует файлы.
4. Батчи по 64 чанка → `POST /embed`.
5. Upsert в `chunks` (`ON CONFLICT (content_hash) DO NOTHING`), затем `chunk_locations`.

### Дешёвый диф

`git ls-files -s` отдаёт **blob sha по каждому файлу без чтения самих файлов**. Одна
команда даёт полное состояние рабочего дерева. Сравнение с `files.blob_sha` в БД
находит изменённое множество за миллисекунды даже на монорепе.

Это делает переключение веток дешёвой операцией, а не катастрофой:

```
.git/HEAD изменился
  → git ls-files -s
  → диф с files
  → перечанковать только различающиеся пути
  → из их чанков посчитать только те content_hash, которых ещё нет в chunks
```

На типичном чекауте между ветками реально эмбеддится несколько десятков чанков.

### Watch-режим

- `chokidar` на корень репозитория, `ignoreInitial: true`,
  `awaitWriteFinish: { stabilityThreshold: 300 }` — иначе поймаем частично записанный
  файл от сборщика.
- Отдельно `.git/HEAD` и `.git/index` — чекауты, ребейзы, `git stash`.
- Debounce 1500 мс, накопление в `Set<path>` (дедуп: сборщики трогают один файл по
  многу раз).
- Очередь с backpressure: если в буфере > 500 путей — переключиться на полный
  `git ls-files -s`-диф, это дешевле поштучной обработки.

### Обработка одного файла

```
blob_sha изменился?  нет → выход
  ├─ файл удалён → DELETE chunk_locations WHERE repo_id, path; DELETE files
  └─ файл изменён:
       чанкуем → считаем content_hash для каждого чанка
       SELECT content_hash FROM chunks WHERE content_hash = ANY($1)
       эмбеддим только недостающие
       BEGIN
         INSERT INTO chunks ... ON CONFLICT DO NOTHING
         DELETE FROM chunk_locations WHERE repo_id=$1 AND path=$2
         INSERT INTO chunk_locations ...
         UPDATE files SET blob_sha, indexed_at
       COMMIT
```

Замена локаций целиком для файла — вместо попыток вычислить дельту по строкам. Проще,
атомарнее, и стоит копейки.

### Сборка мусора

Раз в час, вне пиковой нагрузки:

```sql
DELETE FROM chunks c
 WHERE NOT EXISTS (SELECT 1 FROM chunk_locations l
                    WHERE l.content_hash = c.content_hash);
```

## 8. Поиск и ранжирование

> **Замерено и опровергнуто (см. §15).** Изначально этот раздел утверждал, что чисто
> векторный поиск недостаточен и гибрид нужен с самого начала. Три golden-набора
> показали обратное: лексическая ветка ни разу не выиграла и дважды заметно
> проиграла — включая набор из одних идентификаторов, где она обязана была быть
> сильной. Режим по умолчанию — `semantic`. Ветка сохранена и описана ниже: она
> стоит 1–2 мс и может понадобиться на корпусе в сотни раз больше нашего.

Исходная гипотеза была такой: векторный поиск проваливается там, где запрос содержит
точное имя символа, а такие запросы Claude задаёт постоянно, — значит нужен гибрид.

### Пайплайн

```
запрос
 ├─ вектор: embed(kind=query) → HNSW top-50
 └─ лексика: to_tsquery + trigram по symbol → top-50
        ↓
   RRF-слияние (k=60)
        ↓
   MMR-диверсификация: не более 2 чанков из одного файла
        ↓
   [Ф6] cross-encoder реранк top-30 → top-8
        ↓
   top-8 с обрезкой по токен-бюджету
```

**RRF** (Reciprocal Rank Fusion) выбран вместо взвешенной суммы скоров сознательно:
косинусная близость и `ts_rank` живут в несопоставимых шкалах, а подбор весов между
ними — бесконечная возня. RRF работает по рангам и не требует калибровки.

```sql
WITH vec AS (
  SELECT l.id, ROW_NUMBER() OVER (ORDER BY c.embedding <=> $1) AS rank
    FROM chunk_locations l JOIN chunks c USING (content_hash)
   WHERE l.repo_id = $2
   ORDER BY c.embedding <=> $1
   LIMIT 50
),
lex AS (
  SELECT l.id, ROW_NUMBER() OVER (ORDER BY ts_rank(c.tsv, q) DESC) AS rank
    FROM chunk_locations l JOIN chunks c USING (content_hash),
         plainto_tsquery('simple', $3) q
   WHERE l.repo_id = $2 AND c.tsv @@ q
   ORDER BY ts_rank(c.tsv, q) DESC
   LIMIT 50
)
SELECT id, SUM(1.0 / (60 + rank)) AS score
  FROM (SELECT * FROM vec UNION ALL SELECT * FROM lex) u
 GROUP BY id
 ORDER BY score DESC
 LIMIT 20;
```

### Токенизация идентификаторов

`scheduleRedelivery` для `to_tsvector('simple', ...)` — один токен, и запрос
`redelivery` его не найдёт. Нужна предобработка `embed_text` перед FTS: разбить
camelCase / snake_case / kebab-case и **дописать** развёрнутые слова к тексту, сохранив
исходные идентификаторы.

`scheduleRedelivery` → `scheduleRedelivery schedule redelivery`

Реализовать как SQL-функцию `code_tokens(text)` и использовать её в generated-колонке
`tsv` (миграция `002_fts.sql`). Без этого лексическая половина гибрида работает вполсилы.

### Диверсификация

Без неё топ-5 регулярно оказывается пятью соседними чанками одного файла — контекст
потрачен, а обзора нет. Жёсткое правило: максимум 2 чанка на файл в выдаче, плюс, по
возможности, минимум 3 разных файла.

## 9. Оценка качества

Раздел, который обычно пропускают, — и потом полгода «улучшают» поиск наугад.

### Golden-набор

`src/eval/golden.jsonl`, **минимум 40 записей**, собранных из реальных вопросов:

```jsonl
{"q": "где обрабатывается повторная отправка платежа",
 "expect": ["packages/queue/src/backoff.ts::scheduleRedelivery"]}
{"q": "как формируется JWT для сервис-сервис вызовов",
 "expect": ["packages/auth/src/tokens.ts::signInternal"]}
{"q": "валидация телефона при регистрации",
 "expect": ["apps/web/src/forms/signup.ts::phoneRule",
            "packages/validators/src/phone.ts::isE164"]}
```

Правило составления: **формулировать запрос так, как его задал бы человек, не знающий
кодовой базы**, и намеренно не использовать слова из имени искомого символа. Иначе
измеряется grep, а не семантика.

**Откуда брать записи.** Не выдумывать за столом. Включить LSP-плагин (§1) и неделю
работать как обычно, записывая каждый вопрос, на который LSP и grep не ответили за
разумное время. Это ровно то множество, ради которого строится индекс, — и потому
единственный честный набор для его оценки. Выдуманные запросы систематически смещены
в сторону того, что мы уже умеем находить.

### Метрики

- `recall@5` — целевая, попал ли ожидаемый символ в топ-5.
- `MRR@10` — чувствительна к позиции, ловит мелкие регрессии ранжирования.
- `p50 / p95` латентности поиска.
- % чанков с `truncated: true` — здоровье чанкера.

`npm run eval` печатает таблицу и дифф к предыдущему прогону. Гоняется на каждое
изменение чанкера, префиксов, весов или модели.

### Что проверить экспериментами

Порядок по ожидаемой отдаче:

1. `task: search result | query: ` **против** `task: code retrieval | query: ` для
   запросов. Второй вариант обучен под наш кейс — вероятный лёгкий выигрыш.
2. Обогащающий заголовок целиком vs без `path-words` vs без `imports`. Проверить, что
   каждая строка заголовка окупается, а не разбавляет вектор.
3. TARGET_TOKENS 200 / 300 / 500.
4. ~~Гибрид vs чистый вектор~~ — **закрыто трижды** (§15, §17): вклад лексики
   отрицательный, режим по умолчанию `semantic`.
5. ~~Matryoshka 768 vs 512 vs 256~~ — **закрыто (§18)**: у EmbeddingGemma усечение
   до 512 стоит 7 п.п. MRR. Экономия памяти того не стоит.

## 10. MCP-сервер

Транспорт stdio, `@modelcontextprotocol/sdk`. Регистрация в `.mcp.json` проекта.

### Инструменты

Один `search_code` — недостаточно: модель регулярно нуждается в уточнении контекста
и в понимании структуры проекта.

**1. `search_code`** — основной.
```ts
{ query: string, k?: number = 8, repo?: string, path_glob?: string,
  lang?: string, mode?: 'hybrid' | 'semantic' | 'lexical' }
```

**2. `find_similar_code`** — смысловые дубли, второй ключевой сценарий.
```ts
{ path: string, symbol?: string, line?: number,
  k?: number = 8, exclude_same_file?: boolean = true }
```
Реализация: берём вектор исходного чанка, ищем ближайшие, исключаем сам чанк.
Точные копии находятся бесплатно — по совпадению `content_hash`.

**3. `expand_context`** — приблизить, если найденный фрагмент оказался коротким.
```ts
{ path: string, start_line: number, end_line: number,
  before?: number = 20, after?: number = 20 }
```
Существует ровно затем, чтобы модель не читала файл целиком ради двадцати строк.

**4. `repo_map`** — структура и экспорты, для ориентации в незнакомом проекте.
```ts
{ repo?: string, path_prefix?: string, depth?: number = 2 }
```

**5. `index_status`** — сколько файлов и чанков, лаг очереди, модель, время последней
индексации. Нужен, чтобы отличить «в коде такого нет» от «индекс отстал на 200 файлов».

### Формат выдачи

Компактный текст, не JSON-простыня. Каждый лишний токен здесь — токен, отнятый у работы.

```
1. packages/queue/src/backoff.ts:47-89  ·  scheduleRedelivery  ·  0.89
   class RedeliveryQueue > method scheduleRedelivery
   > Schedules a failed payment for another delivery attempt with exponential backoff.
   export async function scheduleRedelivery(payment: Payment, attempt: number) {
     const delay = Math.min(BASE_DELAY * 2 ** attempt, MAX_DELAY)
     ...

2. packages/payments/src/gateway.ts:203-231  ·  handleWebhookFailure  ·  0.74
   ...
```

Жёсткие правила формата:

- Хедер строки — всегда `path:start-end`. Это кликабельно в терминале и сразу годится
  для `Read`.
- Тело — максимум 15 строк на попадание, с обрезкой посередине для длинных.
- Общий бюджет ответа — **4000 токенов**, режем по мере набора.
- В конце — подсказка: `используйте expand_context для полного тела`.

### Описания инструментов

Описание — это промпт, по которому модель решает, звать ли инструмент. Формулировать
явно и с указанием границ:

> `search_code` — найти код по смыслу описания, а не по точному имени. Используйте,
> когда не знаете, как называется искомая функция или файл: «где обрабатывается
> повторная отправка платежа», «как реализована инвалидация кеша». Для поиска по
> известному имени символа используйте Grep — он быстрее и точнее.

Последнее предложение важно: без него модель начнёт звать семантический поиск вместо
grep там, где grep лучше.

scs repo add /path/to/repo --name acme    # регистрация

- Postgres слушает `127.0.0.1:5433`, отдельная роль `scs`, отдельная БД.
- Эмбеддинг-сервис слушает `127.0.0.1:8077`, никаких внешних интерфейсов.
- MCP работает по stdio — сетевого surface нет вообще.
- Никаких портов наружу и туннелей не требуется: инициатором соединения всегда
  выступает локальный клиент.
- Deny-list секретов (§6) — считать частью threat model, а не косметикой.

| **Критерий §1** | recall@5 = 46.6% при целевых 85% | разрыв разобран экспериментально, план — [`docs/RECALL85.md`](RECALL85.md): измеренная связка этапов даёт 58.6%, дальше — описания назначения |
| **Мульти-репо в MCP** | открытый вопрос №3 (§14) | ждёт сценария, на котором это можно измерить, а не решить умозрительно |

**Про критерий 85%.** Он не достигнут, и честнее сказать, чем именно он
ограничен. Ответ есть в первых 300 кандидатах в 82.8% случаев — то есть
17 п.п. недостижимы вообще ничем поверх текущей схемы «вопрос → фрагмент
кода». Оставшиеся 36 п.п. между 46.6% и 82.8% — это ранжирование, и три
приёма (приоритеты, реранкер, ремонт чанкера) отыграли из них меньше
половины. Дальше нужен не пятый множитель к скору, а промежуточное
представление: описание НАЗНАЧЕНИЯ кода, а не его текста. Это другой проект,
и начинать его стоит с замера, а не с реализации.

### Почему порядок именно такой

**Ф4 выполнена и переставила всё остальное.** Вывод «гибрид не нужен» подтвердился
на 39 655 чанках (Sourcegraph на большом масштабе пришёл к обратному — у нас не
воспроизвелось). Зато рухнул recall: 87.5% на самодельном наборе против 37.9% на
наборе из транскриптов. Разница не в масштабе индекса, а в честности запросов (§17).

**Ф5 теперь первая, и не по той причине, что раньше.** Прежний аргумент был «нельзя
портировать на NPU модель, которая хуже альтернатив». Новый сильнее: замер ранга
показал, что треть правильных ответов отсутствует даже в первых 300 кандидатах, —
это потолок модели, и он ниже требуемого. `embeddinggemma-300m` выбрана не за
качество, а за то, что она единственная официально поддержана Ryzen AI 1.8. Если
разрыв с `Qwen3-Embedding-0.6B` велик, под вопросом оказывается сама привязка к NPU
(например, оставить GPU и на проде).

**Ф8 больше не безнадёжна, но всё ещё вторая.** Раньше довод был такой: правильный
ответ на 110-м месте из 157, реранкер до него не дотянется. Теперь есть
распределение по всему набору: @5 = 37.9%, @50 = 56.9%. Девятнадцать пунктов
реранкеру доступны — но поднимать порядок внутри пула, где ответа нет в трети
случаев, значит чинить симптом.

Правило, подтверждённое теперь трижды: измерение идёт раньше оптимизации. Префикс
`code retrieval` и приоритет по графу ссылок выглядели убедительно на одиночных
примерах и были отвергнуты замером. Ф4 добавила к списку два случая, где интуиция
ошиблась в обратную сторону: узкое место скорости оказалось не в GPU, а в пробелах
на входе токенизатора, и HNSW-индекс полтора месяца не использовался вообще.

## 15. Что показала реализация

Ф0–Ф3 реализованы и работают. Ниже — только то, что разошлось с этим документом.
Все числа получены командой `scs eval` на трёх golden-наборах.

### Гибридный поиск не окупился

| golden-набор | запросов | hybrid MRR | semantic MRR |
|---|---|---|---|
| `acme` (фикстура, русские запросы) | 14 | 0.899 | 0.899 |
| `scs` (свой код, в осн. русские) | 24 | 0.734 | **0.807** |
| только идентификаторы, английский | 12 | 0.917 | **1.000** |

Лексическая ветка **ни разу не выиграла и дважды проиграла**. Решающий замер — третий:
на запросах вида `missingHashes`, `splitOversized oversized function` чистый вектор дал
идеальные 100% recall и MRR 1.000, а RRF-слияние его испортило. Когда сильная ветка уже
права, слияние со слабой может только ухудшить.

Снижение `lexicalWeight` улучшало гибрид монотонно (MRR 0.734 → 0.743 → 0.765 при
0.5 → 0.25 → 0.1), то есть оптимум лежит в нуле.

Итог: `search.defaultMode = 'semantic'`. **Оговорка:** корпуса маленькие (170 и 23 чанка).
На настоящей монорепе в 50k чанков у вектора будет несравнимо больше поводов запутаться,
и вывод нужно перепроверить — ветка и `scs eval` для этого готовы.

### Префикс `code retrieval` — ложный след

Одиночный замер выглядел убедительно: на провальном запросе он поднял нужный чанк
с 0.087 до 0.301, в 3.5 раза. На полном наборе выигрыша нет — recall@1 подрос,
но recall@5 упал с 87.5% до 79.2%, а MRR не сдвинулся. Оставлен
`task: search result | query: `.

Это лучшая иллюстрация того, зачем §9 стоит раньше §10: по одному примеру был бы
сделан неверный вывод.

### Лексический индекс строился по обогащённому тексту

`tsv` считался по `embed_text`, то есть вместе с заголовком, где лежит список **всех**
экспортов файла. Из-за этого запрос с именем любого символа лексически совпадал со всеми
чанками файла сразу. Исправлено миграцией `004_fts_rawtext.sql` — теперь по `raw_text`.
На метриках это не отразилось (набор недостаточно нагружает лексику), но механизм был
явно неверен.

### Карточки файла переоценивались ранжированием

`file_card` короткая и плотно набита идентификаторами, поэтому `ts_rank` и вектор
систематически ставили её выше настоящей реализации. Введён `search.fileCardPrior = 0.6`.
Это подняло **обе** ветки: semantic MRR 0.881 → 0.929 на `acme`.

### Обогащающий заголовок удорожает инкрементальные правки

В заголовок входит список экспортов файла, поэтому добавление одной экспортируемой
функции меняет `content_hash` **всех** чанков этого файла и требует их пересчёта.
Замерено: правка одного файла — 4 чанка вместо 1.

Переиспользование между ветками при этом работает как задумано: возврат файла к прежнему
состоянию дал `посчитано векторов 0, переиспользовано 3`.

Компромисс осознанный — заголовок повышает качество поиска, а файл всё равно правится
целиком. Но проверить вклад строки `exports:` отдельным замером стоит.

### Чанкер на TypeScript Compiler API вместо tree-sitter

`ts.createSourceFile` — чистый JS без node-gyp, что важно, потому что целевая машина
другая (AMD, возможно Windows). Из коробки даёт JSDoc и модификаторы экспорта.
Используется только парсер, без `Program` и чекера, поэтому tsconfig проекта не нужен.
Интерфейс оставлен расширяемым: tree-sitter добавляется для Go/Python отдельным модулем.

### Незакоммиченные файлы были невидимы

`git ls-files -s` показывает только отслеживаемые файлы. Документ подавал это как
достоинство («.gitignore соблюдается бесплатно»), умалчивая о следствии: только что
созданный файл не попадает в индекс до первого `git add`, а незакоммиченный код — ровно
тот, по которому ищут чаще всего. Добавлен `git ls-files --others --exclude-standard`
плюс `git hash-object` для вычисления того же sha, который появится после `git add`
(поэтому добавление в индекс не вызывает пересчёта).

### Найденные при разработке дефекты

- **Диапазоны строк выворачивались наизнанку** (`L20-7`): `preamble` добавлялся в конец
  списка кусков, хотя физически стоит первым, и `mergeSmall` склеивал его с последней
  функцией. Закрыто тестами в `test/chunker.test.ts`.
- **zod v4** больше не прогоняет `.default()` через парсинг — вложенные умолчания
  не применялись, и `cfg.embed.url` был `undefined`. Нужен `.prefault()`.
- **Проверка на бинарник** сравнивала с пробелом вместо нулевого байта.
- **PG18** сменил конвенцию каталога данных: монтировать надо `/var/lib/postgresql`.

### Разбор аналогов и что из них взято

Сравнивались grepai, Cursor, Aider и Sourcegraph Cody.

**Взято.** Штрафы по шаблонам пути (`search.penalties`) — идея из
`grepai search.boost.penalties`. Разрезание чанка при переполнении контекста вместо
тихой обрезки — идея из `grepai ReChunk()`.

**Отвергнуто после проверки: приоритет по графу ссылок (Aider PageRank).**
Гипотеза звучала убедительно — «функция, вызываемая из двадцати мест, важнее
приватного хелпера». Проверка на нашем корпусе её опровергла: у `toVectorLiteral`
(наш худший ложноположительный результат) **4** ссылки, у `missingHashes`
(правильный ответ) — **2**, а у `diversify` и `splitOversized`, которые тоже
являются правильными ответами в golden-наборе, — по одной.

Причина расхождения в разнице задач. Aider выбирает, **какие файлы показать
в обзоре репозитория**, — там популярность символа и есть его важность. Мы отвечаем
на **конкретный вопрос**, а ответом на конкретный вопрос чаще оказывается узко
используемая функция. Приоритет по популярности здесь анти-коррелирует с целью.

**Не взято: Merkle-дерево (Cursor).** Оно решает задачу синхронизации клиент-сервер.
Для git-репозитория `git ls-files -s` даёт то же самое дешевле — git уже
поддерживает эти хэши. Кэширование эмбеддингов по хэшу чанка Cursor реализовал
независимо от нас, что подтверждает правильность §5.

**Не взято: собственный граф вызовов (grepai `trace`).** Противоречит §1: LSP
отвечает на «кто вызывает» с гарантией полноты, а `trace` в режиме `fast` работает
регулярками. Ставить приблизительный граф рядом с точным LSP — регресс.

**Не взято: мультиязычность через tree-sitter (grepai поддерживает 11 языков).**
Проверено на целевом корпусе: в `unitify` 3966 `.js`, 1513 `.tsx`, 1276 `.ts` —
наш чанкер покрывает всё. Остальное — 1910 `.njk` и 141 `.graphql`, то есть шаблоны
и схемы, а не бизнес-логика. Возвращаться, только если появится репозиторий с Go
или Python. Единственный реальный пробел по форматам — Markdown, и он вынесен в Ф4.1.

**Не взято: хранилище без Postgres (grepai `store.backend: gob`).** Единственный файл
вместо СУБД снимает главный барьер установки, и для раздачи инструмента наружу это
было бы правильно. Но Postgres с pgvector у нас уже поднят и работает, так что
ценность сейчас околонулевая. Пересмотреть, если проект будет распространяться.

**Чем мы объективно сильнее.** У grepai чанкинг — `size: 512, overlap: 50`, то есть
фиксированная нарезка (tree-sitter у него только для графа вызовов, и лишь в режиме
`precise` с CGO). Обогащающего заголовка нет ни у одного из четырёх. Встроенного
измерения качества нет ни у одного — при том, что у grepai тоже есть гибрид на RRF
и никакого способа проверить, помогает ли он.

**Оговорка от Sourcegraph.** Cody [отказался от эмбеддингов](https://sourcegraph.com/docs/cody/faq)
в пользу keyword + структурного поиска. Две из трёх причин к нам не относятся
(утечка в сторонний API — мы локальны; масштаб 100k+ репозиториев — не наш), но
третья честна, и они заявляют «equal or better quality» после отказа. Наш вывод
о бесполезности лексики получен на 170 чанках и на монорепе вполне может
развернуться в другую сторону.

### Приоритеты ранжирования: что измерилось, а что нет

| изменение | scs | acme | идентификаторы |
|---|---|---|---|
| исходное состояние | 0.807 | 0.929 | 1.000 |
| + пропорциональный заголовок | 0.806 | **0.964** | 0.958 |
| + штрафы по шаблонам пути | 0.806 | 0.964 | 0.958 |

**Пропорциональный заголовок** — строки `repo/file/path-words/exports/imports`
одинаковы для всех чанков файла, и на коротком чанке они составляют большую часть
входа модели: вектор описывает файл, а не функцию. У `toVectorLiteral` было
47 токенов кода при 78 токенах заголовка. Теперь при нехватке места строки
отбрасываются от наименее специфичных к наиболее; `repo/file/scope/doc` остаются всегда.

Итог: один запрос в acme поднялся со 2-го места на 1-е, один в наборе идентификаторов
съехал с 1-го на 2-е (recall@5 везде не пострадал). На агрегате это размен. Оставлено,
потому что выигрыш пришёлся на recall@1, а просевший набор наполовину состоит из голых
имён символов — то есть из запросов, для которых описание `search_code` прямо велит
брать Grep.

**Штрафы по шаблонам пути на наших корпусах не измеряются вовсе**: тестовые файлы
не попадают в топ ни по одному запросу из наборов. Механизм проверен модульными
тестами (`test/priors.test.ts`), а не метриками. На реальной монорепе с большим
объёмом тестов и фикстур эффект должен появиться — но пока это ожидание, а не факт.

### Тихая потеря кода из индекса

Отдельный класс дефектов, найденный при доработке: код, не попавший в индекс, нельзя
найти ни семантикой, ни лексикой, и **никакой ошибки при этом не возникает**. Таких
мест было два — обрезка чанка по контексту модели и обрезка длинной шапки файла.
Оба заменены на разрезание. Закрыто тестом «ни одна строка файла не пропадает
из индекса».

> **Этого оказалось мало.** Закрыты были два частных случая, а общее правило
> «файл покрывается чанками целиком» сформулировано не было — и дефект вернулся
> третьим способом: всё между объявлениями молча выпадало из индекса. Нашлось
> только на настоящей монорепе и стоило 15 п.п. полноты. См. §19.

изолированные от остальных данных инстанса. `docker-compose.yml` оставлен как
необязательный запасной вариант на порту 5440.

## 16. Проверка на реальной нагрузке: телеметрия роя агентов

Замер снят на живой работе — три роя агентов по задачам вёрстки. Это первые данные
о том, на что инструмент будет тратиться на самом деле, и они меняют приоритеты.

### Исходные цифры

Рои: 37.8 мин (mobile-filter), 21.1 мин (sign-in — **умер на лимите контекста**),
86.5 мин (case-animation). Разбор 635 tool-вызовов последнего:

| категория | вызовов | доля | закрываем? |
|---|---|---|---|
| grep по исходникам | 170 | 30.0% | **частично** — только там, где имя неизвестно |
| чтение файлов через sed/cat/head | 152 | 26.9% | **да** — ради этого сделан `expand_context` |
| прочее | 98 | 17.3% | неизвестно |
| grep по **собранному CSS** | 92 | 16.3% | **нет, по устройству** |
| `git show` удалённых SCSS | 28 | 4.9% | нет → выносится в Ф10 |
| jest / playwright / tsc / build | 23 | 4.0% | нет |

Все детерминированные команды за 86-минутный рой — 6–8 минут. Ядер 24, лимит
параллелизма 16: железо не было узким местом ни секунды. Остальные ~90% — инференс.

### Главный вывод: ускорять инструменты бессмысленно

Раз детерминированные команды занимают 6–8 минут из 86, то скорость самих
инструментов роли не играет: наш поиск отвечает за 90–130 мс, grep тоже быстрый,
экономия — секунды.

Работает другой механизм: **каждый вызов инструмента стоит хода модели**, а ходы
модели и есть те ~78 минут. Ценность не в скорости вызова, а в сокращении их числа.

Оценка с явными допущениями: если из 322 адресуемых вызовов (grep по исходникам +
чтение файлов) половина схлопывается в ~50 вызовов `search_code`, это −110 вызовов,
около −17%. При допущении о пропорциональности ходов числу вызовов — примерно
**−13 минут из 86**. Ощутимо, но это не разница между 86 и 20.

**Это оценка, а не замер.** Настоящий коэффициент даёт Ф4.2.

### Где выигрыш крупнее, чем в скорости

Один из трёх роёв умер на лимите контекста. 152 чтения файлов целиком через
`sed/cat/head` — это и есть сожжённый контекст. `search_code` отдаёт до 4000 токенов
сфокусированной выдачи вместо файла целиком.

Эффект двойной: меньше контекста — это не только меньший риск упереться в лимит,
но и быстрее каждый ход, потому что длинный контекст замедляет инференс. По токенам
это другой порядок величины, чем −17% вызовов.

### Граница применимости, подтверждённая данными

18.9% вызовов (собранный CSS + история git) наш индекс не покрывает. Для собранного
CSS это осознанно и навсегда: артефакт сборки лежит в deny-листе (§6), а искать класс
в сгенерированном файле — точная задача, grep для неё лучше по существу. Для истории
git — открывается Ф10.

### Чего инструмент не чинит вообще

**442 из 566 Bash-вызовов (78%) — агенты заново добывают одни и те же факты.**
Вызовов на агента: 64, 59, 59, 58, 53, 47, 47, 45, 43, 39, 26, 26 — каждый из 12
агентов делал собственный полный проход разведки. Пять линз аудита независимо
перечитали те же два удалённых листа и заново прогрепали тот же собранный CSS.

Семантический поиск делает каждое переоткрытие дешевле, но **12 агентов ×
избыточная разведка остаётся 12×**. Это архитектура роя, а не задача retrieval.
Причём в цепочке (досье → миграция → интеграция → аудит → рефьютеры → e2e) стадия
досье уже есть — значит, либо она не несёт достаточно, либо следующие стадии ей
не доверяют и перепроверяют.

Общий кэш разведки сократит больше, чем более умный поиск. Наш индекс даёт для этого
кирпич — он общий для всех агентов, а `repo_map` заменяет полный проход разведки
одним вызовом, — но дисциплины роя установка scs не создаёт. Записано здесь, чтобы
инструмент не продавался как решение чужой проблемы.

## 17. Ф4: что показала настоящая монорепа

Всё, что было измерено до этого раздела, измерялось на 170 и 23 чанках. Здесь —
`unitify`: 7168 файлов, **39 655 чанков**, в 230 раз больше. Результаты меняют
приоритеты сильнее, чем любой предыдущий замер.

Golden-набор — 58 запросов, собранных из **72 транскриптов реальной работы агентов**
в этом репозитории (`src/eval/golden.unitify.jsonl`), а не выдуманных за столом.
Каждая запись проверена машинно: путь существует в `git ls-files`, символ объявлен
в этом файле. Запросы намеренно не содержат слов из имени искомого символа — иначе
измерялся бы grep.

### Главный результат: recall@5 = 38% при целевых 85%

| режим | recall@1 | recall@5 | recall@10 | MRR | p50 |
|---|---|---|---|---|---|
| semantic | 13.8% | **37.9%** | 43.1% | 0.227 | 87 мс |
| hybrid | 10.3% | 36.2% | 43.1% | 0.196 | 90 мс |
| lexical | 1.7% | 1.7% | 1.7% | 0.017 | 14 мс |

На корпусе своего кода те же метрики были 87.5% и 0.806. **Разрыв не в масштабе
индекса, а в том, что запросы наконец настоящие.** Наши прежние наборы писались
человеком, который знал ответ; транскриптные — теми, кто искал вслепую.

Вывод о лексике подтверждён в третий раз и теперь на большом корпусе: гибрид снова
проиграл чистому вектору. `lexical` даёт 1.7% просто потому, что в честно
сформулированных запросах нет слов из кода — ровно того случая, ради которого
затевался семантический поиск.

### Это провал полноты, а не ранжирования

Ключевой диагностический замер — ранг правильного ответа в чистой векторной выдаче
без приоритетов и диверсификации:

| глубина | @1 | @5 | @10 | @50 | @300 |
|---|---|---|---|---|---|
| весь индекс | 8.6% | 39.7% | 44.8% | 56.9% | **67.2%** |
| только код (без документации) | 17.2% | 41.4% | 46.6% | 60.3% | 67.2% |

**Треть ожидаемых ответов не встречается вообще нигде в первых 300 из 39 655.**
Никакой реранкер этого не чинит: он переупорядочивает то, что уже отобрано.
Между @5 и @50 есть 19 п.п. запаса — вот это реранкеру доступно, но потолок
всё равно 67%, и определяется он моделью.

Отсюда окончательный порядок: **сначала Ф5 (модель), потом Ф8 (реранкер)**.
Причём Ф5 приобретает новый аргумент, которого не было раньше: запросы русские,
код английский, а `embeddinggemma-300m` выбиралась по совместимости с NPU,
а не по мультиязычности. `Qwen3-Embedding-0.6B` становится первым кандидатом.

### Документация в индексе: помогает людям, мешает метрике

Ф4.1 добавила Markdown (3503 секции в `unitify`). Замер её цены:

- документация занимает **31.6% мест в топ-10**;
- recall@1 без неё 17.2% против 8.6% с ней — то есть на первом месте она
  вытесняет код вдвое чаще, чем помогает;
- на recall@5 разница почти исчезает (41.4% против 39.7%).

Механизм видно в промахах: на запрос «как понять, что фоновые обработчики
перестали шевелиться» первые три места занимает `docs/cron-monitoring-panel-plan.md`,
а не `cronHealthWatchdog.ts::decideCanaryAlert`. Формально документ **отвечает**
на вопрос лучше кода — но golden-набор ждёт код, и агенту чаще нужен код.

Решение отложено до Ф5 сознательно: понижающий приоритет для документации
подгонит ранжирование под текущую модель, а модель, вероятно, сменится.
Индексацию документации оставляем — она нужна для вопросов «как это устроено
вообще», которых в наборе мало по построению.

### Пробел, который стоил бы недели: эмбеддер упирался в CPU, а не в GPU

Первый же прогон показал 1.9 чанка/с — это 7 часов на монорепу и невыполненный
критерий §1. При этом GPU загружен на 1–10%, а рантайм Ollama жжёт ~300% CPU.
Виноват не инференс, а подготовка входа, и конкретно — **серии пробельных
символов**, то есть отступы и переносы строк. Замер на одном наборе чанков:

| вход | скорость |
|---|---|
| как есть | 1.9 чанк/с |
| переносы → пробел | 2.9 чанк/с |
| схлопнуть все пробельные серии | **91.3 чанк/с** (×48) |

Цена по качеству измерена парным тестом на 47 парах «запрос → ожидаемый чанк»:
средняя близость 0.3600 против 0.3638, схлопывание выигрывает в 19 случаях
из 47. То есть разницы нет, а ускорение — полтора порядка.

Нормализация включена в `services/embed-ollama` и входит в идентификатор модели
(`embeddinggemma:300m+ws`), поэтому её переключение автоматически обесценивает
индекс и не смешивает несравнимые вектора.

Обобщение, которое стоит помнить: **узкое место оказалось не там, где его
искали.** Проект полгода рассуждал про NPU против GPU, а решающим фактором
скорости оказался токенизатор на CPU.

### HNSW не использовался вообще

`EXPLAIN` показал полный перебор всех 39 655 векторов: 194 мс на запрос.
Причина не в настройках индекса, а в форме запроса — пока `ORDER BY` стоит над
join'ом `chunk_locations` с `chunks`, планировщик не может применить индекс,
построенный на `chunks`. Отбор перенесён в подзапрос по одной таблице.

| вариант | латентность | совпадение с точной выдачей |
|---|---|---|
| было: join + сортировка | 194 мс | 100% (это и есть точный перебор) |
| HNSW, `ef_search` = 40 (умолчание pgvector) | 3 мс | 69% |
| HNSW, `ef_search` = 200 | **5 мс** | **97%** |
| HNSW, `ef_search` = 600 | 80 мс | 100% |

Взято 200. Отдельно убран join с материализованной CTE `filtered` в финальной
выборке — он давал полный проход по локациям ради полусотни строк. Итог по
всему `search()`: **274 мс → 87 мс**, из которых 70–90 мс — это эмбеддинг самого
запроса, то есть SQL перестал быть заметной частью.

Оговорка: при фильтрах по пути или языку приближённый отбор может не набрать
кандидатов, поэтому там сохранён точный перебор. Это осознанный размен
корректности на скорость в пользу корректности.

### Стоимость индекса

| | значение |
|---|---|
| файлов проиндексировано | 7047 из 7168 (121 пропущен: бинарники, минифицированное) |
| чанков | 39 655 |
| время полной индексации | **18 минут** (36.6 чанк/с сквозной, вместе с БД) |
| обрезано по контексту модели | 0.2% (порог тревоги — 5%) |
| таблица `chunks` | 426 МБ |
| HNSW-индекс | 158 МБ |
| база целиком | 452 МБ |

Оценка §5 («40–60k чанков, HNSW 150–250 МБ») подтвердилась почти точно.
Критерий §1 «первичная индексация — минуты, не часы» выполнен, но только
благодаря находке с пробелами.

Распределение чанков по типам: function 10 743, preamble 7695, type 6108,
component 5839, section (документация) 3503, file_card 3353, method 2197,
class 217.

### Что из этого следует для плана

1. **Ф5 переходит в критический путь.** Не «полезно сравнить модели», а «без
   этого проект не выполняет свою задачу»: 67% потолок полноты — это про модель.
2. **Ф8 остаётся после Ф5**, но перестаёт быть безнадёжной: 19 п.п. между @5 и @50
   реранкер способен отыграть — после того, как модель поднимет сам потолок.
3. **Приоритет документации против кода** — отдельная задача, но только после Ф5.
4. Критерий успеха §1 (recall@5 ≥ 0.85) на честном наборе **не достигнут** и
   пока не должен считаться достигнутым ни на каком другом.

## 18. Ф5: сравнение эмбеддинг-моделей

Ф4 показала, что потолок полноты (67% при глубине 300) определяется моделью.
Ф5 отвечает, можно ли этот потолок сдвинуть сменой модели, и заодно называет
цену привязки к NPU.

Все три модели проиндексировали `unitify` целиком (по ~39 700 чанков каждая) и
прогнали на одном и том же наборе из 58 транскриптных запросов. Qwen3 отдаёт
1024 измерения и усечена по Matryoshka до 768 — схема БД фиксирует размерность.

| модель | recall@1 | recall@5 | recall@10 | MRR | @300 | индексация |
|---|---|---|---|---|---|---|
| **embeddinggemma-300m** | **13.8%** | **37.9%** | **43.1%** | **0.227** | **67.2%** | 18 мин |
| Qwen3-Embedding-0.6B (768d) | 10.3% | 24.1% | 29.3% | 0.163 | 65.5% | 29 мин |
| jina-embeddings-v2-base-code | 1.7% | 5.2% | 5.2% | 0.025 | 19.0% | 11 мин |

### Что это значит

**Привязка к NPU ничего не стоит.** Главный риск проекта был в том, что
`embeddinggemma-300m` выбрана по совместимости с Ryzen AI, а не по качеству.
Замер закрывает вопрос: из трёх кандидатов официально поддержанная AMD модель
оказалась лучшей. Открытый вопрос №2 (§14) закрыт.

**`jina-embeddings-v2-base-code` непригодна здесь, и причина не в коде,
а в языке.** Модель англоязычная, а 52 из 58 запросов — русские. Медианный ранг
правильного ответа 88, в первых трёхстах его нет в 47 случаях из 58. «Заточена
под код» не помогает, если вопрос задан не на том языке, под который она обучена.
Это одновременно предупреждение: набор из английских запросов дал бы совсем
другую картину, и по нему мы выбрали бы неверную модель.

**Qwen3 проиграла по существу, а не из-за усечения.** Гипотеза «виновата
Matryoshka 1024 → 768» проверена отдельно: на общем пуле из 3047 чанков
(47 отвечаемых запросов, замер целиком в памяти, без БД) варианты неразличимы.

| вариант | recall@1 | recall@5 | MRR |
|---|---|---|---|
| qwen3 1024d | 53.2% | 74.5% | 0.622 |
| qwen3 768d (усечение) | 57.4% | 72.3% | 0.641 |
| qwen3 512d | 57.4% | 74.5% | 0.640 |
| **gemma 768d** | **68.1%** | **78.7%** | **0.742** |
| gemma 512d | 57.4% | 74.5% | 0.669 |

Абсолютные числа здесь выше, чем в основной таблице, просто потому, что пул
в тринадцать раз меньше корпуса; сравнивать между собой можно только строки.

Побочный результат закрывает ещё один пункт из списка экспериментов §9:
**Matryoshka до 512 для EmbeddingGemma обходится в 7 п.п. MRR** — вчетверо
меньшая память того не стоит. Для Qwen3 усечение бесплатно, но она проигрывает
и в полной размерности.

### Чего Ф5 не дала

Потолок не сдвинулся: 67.2% против 65.5% — обе модели не находят треть ответов
вообще. Значит, дело не в выборе между этими моделями, а в чём-то общем для них.
Наиболее вероятный кандидат виден из провала jina: **запросы русские, код
английский**. Следующий замер — тот же набор, переведённый на английский,
на том же индексе. Если recall заметно вырастет, узкое место межъязыковое,
и лечится оно дёшево (перевод запроса на стороне MCP), а не сменой модели.

### Как воспроизвести

```bash
SCS_EMBED_PORT=8078 SCS_EMBED_MODEL=qwen3-embedding:0.6b npm run embed &
scs repo add /path/to/repo --name repo-qwen
SCS_EMBED_URL=http://127.0.0.1:8078 scs index repo-qwen
SCS_EMBED_URL=http://127.0.0.1:8078 scs eval repo-qwen --golden src/eval/golden.unitify.jsonl
SCS_EMBED_URL=http://127.0.0.1:8078 scs depth repo-qwen --golden src/eval/golden.unitify.jsonl
```

Вектора разных моделей сосуществуют в одной таблице: `model_id` входит
в `content_hash`, а поиск фильтрует кандидатов по модели текущего эмбеддера.
Без этого фильтра приближённый отбор тратил бы кандидатов на чужое векторное
пространство — молча, потому что запрос при этом не падает.

Префиксы каждой модели заданы таблицей в `services/embed-ollama`. Модель, которой
в таблице нет, сервис запускать отказывается: прогон без префиксов не падает,
а тихо ухудшает качество — ровно тот класс отказов, который этот проект ловит
принудительно.

## 19. Ф5.1: потолок оказался нашим дефектом, а не свойством модели

Ф5 оставила гипотезу: потолок полноты 67% одинаков у разных моделей, значит
причина общая. Первый подозреваемый — межъязыковой разрыв (запросы русские,
код английский). Проверка его отвергла и вывела на настоящую причину.

### Межъязыковой разрыв: гипотеза отвергнута

Весь набор переведён на английский (`golden.unitify-en.jsonl`, те же `expect`)
и прогнан на том же индексе:

| набор запросов | recall@5 | MRR | @300 | не найдено |
|---|---|---|---|---|
| русские | 37.9% | 0.227 | 67.2% | 19 из 58 |
| английские | 29.3% | 0.189 | **67.2%** | **19 из 58** |

Решает не сравнение процентов (английский набор чуть труднее: запрет на слова
из имени символа увёл формулировки дальше от поверхностной лексики), а
пересечение промахов: **16 из 19 ненайденных совпадают**. Перевод не открывает
ответы, которых не было, — язык запроса не при чём.

### Настоящая причина: треть кодовой базы не попадала в индекс

Проверка «а существует ли вообще ожидаемый символ среди локаций индекса»
показала, что **13 записей из 58 не могли быть найдены никогда**. Дальше стало
хуже: чанкер индексировал только узлы AST, которые считал кандидатами, плюс
шапку файла. Всё остальное молча выпадало.

На целевой монорепе это:

| что терялось | сколько |
|---|---|
| `const X = new Schema(...)`, крупные конфиги и таблицы констант | 6504 объявления |
| файлы, экспортирующие через `module.exports` (символы не помечались экспортируемыми) | 2174 файла |
| произвольный код между объявлениями | не считали, но это остаток |

Для Keystone-подобной базы `const UserRightsSet = new GQLListSchema(...)` —
это не «константа», а собственно доменная логика. Она уходила в `preamble`,
теряла имя и не находилась по нему в принципе.

Показательно, что §15 уже объявляла этот класс дефектов закрытым. Закрыты были
два частных случая — обрезка длинной шапки и обрезка переполненного чанка.
Общее правило «файл обязан покрываться чанками целиком» тогда сформулировано
не было, и дефект вернулся в третьем месте.

Исправлено тремя изменениями в чанкере:

1. Крупная именованная привязка верхнего уровня стала кандидатом с видом
   `binding` и своим именем.
2. Покрываются **все** промежутки между кандидатами, а не только шапка. Мелкие
   приклеиваются к предыдущему куску — они физические соседи, поэтому диапазон
   строк остаётся честным.
3. Распознаётся CommonJS-экспорт (`module.exports = {...}`, `exports.foo = ...`):
   теперь он попадает в строку `exports:` обогащающего заголовка и в `repo_map`.

### Что дал ремонт

Индекс вырос с 39 655 до 54 237 чанков (+37%), при этом половина векторов
переиспользована по `content_hash` — контент-адресуемость из §5 отработала
ровно как задумано.

| метрика | до ремонта | после |
|---|---|---|
| recall@5 | 37.9% | 37.9% |
| recall@10 | 44.8% | **51.7%** |
| @50 (глубина пула) | 56.9% | **67.2%** |
| @300 (потолок полноты) | 67.2% | **82.8%** |
| ответ не найден вовсе | 19 из 58 | **10 из 58** |
| recall@1 | 8.6% | 5.2% |

Читать это надо так: **потолок был не свойством модели, а нашим дефектом.**
Ответ теперь есть в индексе почти всегда. Просадка @1 — плата за то, что корпус
вырос на 37%: конкуренция в самом верху выдачи усилилась.

### Диагноз сменился на противоположный

Было: провал полноты, реранкер бесполезен, чинить моделью. Стало: между @5
(37.9%) и @50 (67.2%) лежат **29.3 п.п.** — ответ в пуле кандидатов есть,
но стоит ниже пятого места. Это ровно та работа, для которой существует
cross-encoder. **Ф8 становится следующим шагом**, и с призом вдвое большим,
чем оценивалось в §17.

Оговорка про Ф5: сравнение моделей (§18) сделано на индексе ДО этого ремонта.
Вывод «EmbeddingGemma лучшая из трёх» он не отменяет — все три работали на
одинаково повреждённом корпусе, — но абсолютные числа там занижены у всех.

Остаточная недостижимость: 1 запись из 58 (`DEFAULT_CURRENCY_CODE`) — короткая
константа, приклеенная к безымянному промежутку. Заводить отдельный вектор
на однострочную константу дороже, чем этот один промах.

### Третий запрос, «работавший» до первого объёма

`scs status` на монорепе завис. Причина того же рода, что и с HNSW: два
`LEFT JOIN` от одной таблицы (`files` и `chunk_locations` по `repo_id`) давали
декартово произведение — 7100 файлов × 54 250 локаций ≈ 385 млн строк до
агрегации `count(DISTINCT ...)`. На корпусе из 33 файлов это 8844 строки,
то есть незаметно. Заменено подзапросами, 2.4 с вместо зависания.

Правило, которое стоит вынести из Ф4–Ф5.1 отдельно: **SQL, не проверенный
на реальном объёме, не проверен вообще.** Три из пяти найденных дефектов —
запросы, корректные по результату и катастрофические по плану.

## 20. Ф8: cross-encoder реранкер

Замер §19 оставил чёткую задачу: между «ответ в первых 50» (67.2%) и «ответ
в первых 5» (37.9%) лежат 29 п.п. чистого порядка. Cross-encoder существует
ровно для этого — он читает пару «запрос ↔ фрагмент» целиком, а не сравнивает
два независимо посчитанных вектора.

Реализация — отдельный сервис `services/rerank-onnx` за HTTP-контрактом
(`POST /rerank`), по той же причине, что и эмбеддер: модель железозависима,
а ядро о железе знать не должно. Отказ сервиса не роняет поиск — клиент
логирует и возвращает исходный порядок.

### Итог

| | recall@1 | recall@5 | recall@10 | MRR | p50 |
|---|---|---|---|---|---|
| без реранкера | 19.0% | 37.9% | 53.4% | 0.280 | 80 мс |
| с реранкером, CPU q8 | 22.4% | 46.6% | 53.4% | 0.320 | 2974 мс |
| **с реранкером, GPU fp16** | **24.1%** | **46.6%** | **53.4%** | **0.333** | **347 мс** |

Recall@5 вырос на 8.7 п.п. при том, что ни одна другая метрика не просела.
Цена на GPU — 347 мс против 80, и это уже приемлемо для постоянного включения.

### Три вещи, без которых он не работал

**Первая: замена порядка вместо слияния.** Естественная реализация — выбросить
скор эмбеддера и отсортировать по cross-encoder. Замер: recall@5 растёт
с 37.9% до 41.4%, но recall@1 падает с 19.0% до 15.5%. Cross-encoder вытаскивает
середину пула, но сдвигает уверенное первое место bi-encoder'а. Обе ветви правы
по-своему, а их шкалы несравнимы — то есть ровно та задача, для которой в §8
уже выбран RRF. Слияние по рангам вместо замены дало +6.9 п.п. и к @5, и к @1
одновременно.

| вес cross-encoder в RRF | @1 | @5 | @10 | MRR |
|---|---|---|---|---|
| без реранкера | 19.0% | 37.9% | 53.4% | 0.280 |
| 0.5 | 22.4% | **46.6%** | **53.4%** | 0.321 |
| 1 | 25.9% | 44.8% | 48.3% | 0.343 |
| 2 | **27.6%** | 44.8% | 50.0% | **0.348** |
| 3 | 25.9% | 44.8% | 48.3% | 0.335 |

Взят 0.5 — единственное значение, которое улучшает всё и не ухудшает ничего.
Вес 2 даёт лучший MRR и @1, но ценой @5 и @10; он уместен, если выдача
читается по первому результату, а не по списку.

**Вторая: какой текст отдавать.** Сначала отдавался путь плюс чистый код —
recall@5 37.9%, то есть ноль пользы. Тот же прогон с обогащённым текстом (тем,
что видела модель при индексации: путь, экспорты, строка документации) — 41.4%.
Cross-encoder читает пару целиком, и человеческие слова в заголовке для него
важнее, чем для эмбеддера.

**Третья: выбор модели.** `bge-reranker-base` (278M) сделал хуже во всём:
recall@1 10.3% против 19.0%, MRR 0.204 против 0.280 — и тем хуже, чем больше
кандидатов ему давали. `bge-reranker-v2-m3` (568M, XLM-R large) — та самая
таблица выше. Мультиязычность решает: запросы русские.

### Стоимость и почему выключено по умолчанию

| настройка | p50 | recall@5 |
|---|---|---|
| 30 кандидатов, 512 токенов | 10058 мс | 37.9% |
| 30 кандидатов, 256 токенов | 5475 мс | 46.6% |
| **20 кандидатов, 256 токенов** | **2974 мс** | **46.6%** |
| 15 кандидатов, 256 токенов | 2286 мс | 44.8% |

Двадцать кандидатов — оптимум: качество как у тридцати, на треть быстрее.

На CPU это было бы в 37 раз медленнее базового поиска, и включать такое
по умолчанию неправильно. На GPU — вчетверо, что по §16 несущественно
(детерминированные команды заняли 6–8 минут из 86-минутного роя). Поэтому
`search.rerank.enabled = true`, но с двумя оговорками в коде: клиент переживает
отсутствие сервиса и возвращает порядок эмбеддера, а `index_status` показывает
состояние реранкера — агент должен видеть, в каком режиме он ищет.

### GPU: разница между «выключено по умолчанию» и «включено»

`onnxruntime-node` привозит CUDA-провайдер, но собран под CUDA 12
(`libcublasLt.so.12`), а на машине CUDA 13.2. Решается без прав root: нужные
runtime-библиотеки ставятся в локальный venv и подсовываются через
`LD_LIBRARY_PATH` (`npm run cuda:libs`, затем `npm run rerank:gpu`).

Дальше выяснилось, что одного GPU мало:

| устройство и точность | 20 пар |
|---|---|
| CPU, q8 | 2626 мс |
| GPU, q8 | 1619 мс |
| **GPU, fp16** | **121 мс** |

Целочисленная квантизация на CUDA почти не даёт выигрыша — провайдеру нужен
fp16. Разница между «GPU» и «GPU правильной точности» здесь больше, чем между
CPU и GPU. Заодно fp16 оказался чуть точнее q8: MRR 0.333 против 0.320.

Поэтому сервис сам пробует GPU+fp16 и падает на CPU+q8 с явным сообщением
в лог. Молча работающий в двадцать раз медленнее сервис — худший исход
из возможных, поэтому отказ обязан быть слышен.

### Где мы теперь по критерию §1

Recall@5 = 46.6% при целевых 85%. Путь от 37.9% до сюда сложился из трёх
независимых слагаемых: ремонт чанкера (+15.6 п.п. полноты, §19), приоритет
документации (+10.4 п.п. к @1) и реранкер (+8.7 п.п. к @5). Потолок полноты
при этом 82.8%, то есть запас на ранжировании ещё есть — но он уже не такой,
чтобы закрыть разрыв целиком.

Честный вывод: цель в 85% на этом наборе достижима либо принципиально иным
классом retrieval (не «вопрос → фрагмент», а с промежуточным описанием
назначения кода), либо пересмотром самого критерия. Набор из транскриптов
намеренно составлен так, что слов из имени символа в запросе нет, — это
верхняя планка сложности, а не средний вопрос агента.

## 21. Закрытие остальных фаз

Ф6, Ф7, Ф9, Ф10 и Ф4.2 сделаны одним заходом. Ниже — только то, что дало
новое знание; остальное описано в README соответствующих модулей.

### Ф6: демон

`chokidar` по рабочему дереву плюс отдельное слежение за `.git/HEAD`
и `.git/index`. Разделение не косметическое: правка файла обрабатывается
точечно, а checkout ветки меняет тысячи файлов, и поштучная обработка там
дороже одного полного дифа по `git ls-files -s`. Очередь схлопывает дубли
(сборщики трогают файл по многу раз), ждёт затишья 500 мс и при накоплении
свыше 500 путей сама переключается на полный проход.

Приёмка: **новый файл виден в поиске через 1151 мс, удаление — через 702 мс**
при целевых 2 с.

Одна вещь всплыла только при реализации: для watch-режима blob sha нельзя
брать из `git ls-files -s`. Файл только что сохранён, в индексе git его новой
версии ещё нет, и диф показал бы, что ничего не изменилось, — правка молча
не попала бы в поиск. Считаем `git hash-object` по рабочему файлу; это тот же
sha, который появится после `git add`, поэтому добавление в индекс не вызывает
пересчёта векторов.

### Ф9: переносимый индекс

`scs export` / `scs import`. Проверка на настоящем цикле: выгрузили 375 чанков,
стёрли их из базы, загрузили обратно, запустили индексацию —
**посчитано векторов 0, переиспользовано 375**. Контент-адресуемость из §5
работает ровно как задумано: переносятся только вектора, локации пересобираются
локально за секунды.

### Ф10: история git

1180 удалённых файлов за 300 коммитов `unitify`, 1166 проиндексировано,
7924 чанка, 206 с. Пути помечаются префиксом `@deleted/` и понижаются
множителем 0.5 — иначе старые версии конкурируют с актуальным кодом, будучи
на него похожими.

Цена измерена, а не предположена: **добавление истории стоило 1.8 п.п.
recall@5 на живом коде** (46.6% → 44.8%). Отсюда режим остаётся отдельной
командой, а не частью обычной индексации.

Попутно нашёлся дефект, который прятался с самого начала: под фильтрами
`--path` и `--lang` поиск падал на числе параметров SQL. Ветка с фильтрами
не использовала параметр модели, а Postgres считает лишний параметр ошибкой.
Проявлялось только на пути, которым до Ф10 никто не ходил.

### Ф7: NPU-бэкенд

`services/embed-npu` — Python, тот же контракт, ONNX Runtime с Vitis AI EP,
бакеты длин (128/256/512/1024/2048), доля графа на NPU в лог при старте.
Проверить на NPU здесь невозможно: машина Intel + NVIDIA. Но проверяемое
проверено на CPU-провайдере, и это не формальность.

**Приёмка по эталону нашла настоящий дефект.** Экспорт EmbeddingGemma отдаёт
два выхода — `last_hidden_state` и `sentence_embedding`. Ручной mean-pooling
по первому давал вектора правильной размерности и правильной нормы, проходящие
все проверки формы, но с косинусом **−0.06** к векторам dev-бэкенда. После
перехода на `sentence_embedding` — **0.993–0.996** и совпадающий порядок
релевантности.

Отсюда правило, добавленное в процедуру приёмки: сравнение с эталонным
бэкендом обязательно и не заменяется проверкой формы ответа. Форма бывает
правильной при полностью неверных векторах, и это тот самый класс отказов,
который проект ловит принудительно.

### Ф4.2: коэффициент схлопывания — оценка §16 была вдвое оптимистичнее

45 цепочек разведки из 26 транскриптов: агент несколько раз переформулирует
поиск и в конце открывает файл. Средняя длина цепочки — 5.8 вызовов. Замена
каждой одним `search_code`:

| глубина выдачи | цепочек схлопнулось |
|---|---|
| топ-5 | 22.2% |
| топ-8 | 22.2% |
| топ-10 | 24.4% |

Экономия по вызовам — **7.3%** (259 → 240). Считали честно: неудачный поиск
добавляет свой вызов к цепочке, а не «в худшем случае как было».

§16 оценивал схлопывание в половину адресуемых цепочек и −17% вызовов.
Замер даёт вдвое меньше. Это не отменяет ценность инструмента, но меняет
формулировку: **основная польза не в сокращении числа ходов, а в экономии
контекста** — тот же §16 показал рой, умерший на лимите контекста после
152 чтений файлов целиком. Четыре тысячи токенов сфокусированной выдачи
вместо файла на тысячу строк — это другой порядок величины, чем 7% вызовов.

Побочное наблюдение из разбора: в этом репозитории агенты **ни разу не звали
инструмент Grep** — вся разведка идёт через Bash (6105 вызовов из 10006,
из них 1043 начинаются с grep). То есть описание инструмента, объясняющее,
когда брать grep вместо семантики, обращено к инструменту, которым здесь
не пользуются.
