# scs — семантический поиск по коду

Локальный индекс кода на эмбеддингах + MCP-сервер для Claude Code. Отвечает на вопрос
«покажи код, который по смыслу про X», когда вы не знаете, как эта штука называется.

Проектный документ со всеми решениями и замерами: [`docs/DESIGN.md`](docs/DESIGN.md).

## Что это даёт

```
$ grep -ril retry .          # ноль совпадений
$ scs search acme "где обрабатывается повторная отправка платежа"
1. packages/payments/src/gateway.ts:4-8   · handleWebhook       · 0.375
2. packages/queue/src/backoff.ts:7-18     · scheduleRedelivery  · 0.343
```

Второй сценарий — смысловые дубли, которые названы по-разному:

```
$ scs similar acme packages/queue/src/backoff.ts 12
2. packages/notify/src/dispatch.ts:6-14   · requeueUndelivered  · 0.714
```

**Это не замена grep и не замена LSP.** Точный поиск по известному имени быстрее делает
grep; «кто вызывает эту функцию» точнее отвечает LSP. Конвейер: семантика находит точку
входа → LSP обходит граф → grep подтверждает.

## Требования

- Node 22+
- PostgreSQL 16+ с расширениями `vector` и `pg_trgm`
- [Ollama](https://ollama.com) с моделью `embeddinggemma:300m`
- git (индексируются файлы репозитория)

## Установка

```bash
npm install
npm run build
ollama pull embeddinggemma:300m
```

### База данных

По умолчанию scs ходит в `postgres://scs:scs@127.0.0.1:5434/scs`. Если своего инстанса
нет, поднимите вложенный:

```bash
docker compose up -d          # pgvector на 127.0.0.1:5440
export SCS_PG=postgres://scs:scs@127.0.0.1:5440/scs
```

Если инстанс уже есть, заведите в нём отдельные роль и базу:

```sql
CREATE ROLE scs LOGIN PASSWORD 'scs';
CREATE DATABASE scs OWNER scs;
\c scs
CREATE EXTENSION vector;
CREATE EXTENSION pg_trgm;
```

### Запуск

```bash
npm run embed &                              # эмбеддинг-сервис на :8077
npx scs migrate
npx scs repo add /path/to/repo --name acme
npx scs index acme
npx scs search acme "инвалидация кеша сессии"
```

## Команды

| Команда | Что делает |
|---|---|
| `scs status` | состояние БД, индекса и эмбеддера |
| `scs repo add <path> --name <n>` | зарегистрировать репозиторий |
| `scs index <repo> [--full]` | проиндексировать (инкрементально по умолчанию) |
| `scs search <repo> <запрос>` | поиск; `-k`, `-m`, `--path`, `--lang` |
| `scs similar <repo> <файл> <строка>` | смысловые дубли фрагмента |
| `scs eval <repo>` | recall@k и MRR на golden-наборе |
| `scs gc` | удалить чанки без ссылок |

## Подключение к Claude Code

`.mcp.json` в корне проекта уже настроен. Пять инструментов:

- `search_code` — поиск по смыслу
- `find_similar_code` — дубли логики
- `expand_context` — окрестности фрагмента без чтения файла целиком
- `repo_map` — структура и экспорты
- `index_status` — отличить «такого кода нет» от «индекс устарел»

## Как это устроено

1. **Чанкинг по AST** (TypeScript Compiler API) — по границам функций, классов и типов,
   а не по 500 символов. К каждому чанку добавляется заголовок с путём, экспортами,
   импортами и первой строкой JSDoc; он идёт в модель, но не показывается человеку.
2. **Контент-адресуемые вектора**: чанк адресуется хэшем содержимого. Переименование
   файла, `git checkout` и скопипащенный код переиспользуют уже посчитанные вектора.
3. **Эмбеддер за HTTP-контрактом** — TS-ядро не знает, Ollama под ним или Vitis AI
   на NPU. Префиксы модели живут в сервисе, а не в клиенте.
4. **Инкрементальность через `git ls-files -s`** — blob sha всех файлов одной командой,
   без чтения содержимого.

## Измеренное качество

`scs eval`, три golden-набора, EmbeddingGemma-300m:

| набор | запросов | recall@5 | MRR |
|---|---|---|---|
| фикстура, русские запросы | 14 | 100% | 0.929 |
| свой код, в осн. русские | 24 | 87.5% | 0.807 |
| идентификаторы, английский | 12 | 100% | 1.000 |

Режим по умолчанию — `semantic`. Гибрид с лексическим поиском **замерен и отключён**:
на всех трёх наборах он не выиграл ни разу и дважды проиграл. Подробности и оговорки —
[`docs/DESIGN.md` §15](docs/DESIGN.md).
