# scs — семантический поиск по коду

Локальный индекс кода на эмбеддингах + MCP-сервер для Claude Code. Отвечает на вопрос
«покажи код, который по смыслу про X», когда вы не знаете, как эта штука называется.

Проектный документ со всеми решениями и замерами: [`docs/DESIGN.md`](docs/DESIGN.md).

## Что это даёт

```
$ grep -ril retry .          # ноль совпадений
$ scs search acme "где обрабатывается повторная отправка платежа"
1. packages/payments/src/gateway.ts:4-8   · handleWebhook       · 0.375
2. packages/queue/src/backoff.ts:7-18     · scheduleRedelivery  · 0.343
```

Второй сценарий — смысловые дубли, которые названы по-разному:

```
$ scs similar acme packages/queue/src/backoff.ts 12
2. packages/notify/src/dispatch.ts:6-14   · requeueUndelivered  · 0.714
```

**Это не замена grep и не замена LSP.** Точный поиск по известному имени быстрее делает
grep; «кто вызывает эту функцию» точнее отвечает LSP. Конвейер: семантика находит точку
входа → LSP обходит граф → grep подтверждает.

## Требования

- Node 22+
- PostgreSQL 16+ с расширениями `vector` и `pg_trgm`
- [Ollama](https://ollama.com) с моделью `embeddinggemma:300m`
- git (индексируются файлы репозитория)

## Установка

```bash
npm install
npm run build
ollama pull embeddinggemma:300m
```

### База данных

По умолчанию scs ходит в `postgres://scs:scs@127.0.0.1:5434/scs`. Если своего инстанса
нет, поднимите вложенный:

```bash
docker compose up -d          # pgvector на 127.0.0.1:5440
export SCS_PG=postgres://scs:scs@127.0.0.1:5440/scs
```

Если инстанс уже есть, заведите в нём отдельные роль и базу:

```sql
CREATE ROLE scs LOGIN PASSWORD 'scs';
CREATE DATABASE scs OWNER scs;
\c scs
CREATE EXTENSION vector;
CREATE EXTENSION pg_trgm;
```

### Запуск

```bash
npm run embed &                              # эмбеддинг-сервис на :8077
npm run cuda:libs && npm run rerank:gpu &    # реранкер на :8090 (см. ниже)
npx scs migrate
npx scs repo add /path/to/repo --name acme
npx scs index acme
npx scs search acme "инвалидация кеша сессии"
npm run daemon &                             # правки видны в поиске за ~1 с
```

Демон ставится как user-level systemd-юнит:

```bash
npm run build
cp packaging/scs-daemon.service ~/.config/systemd/user/
systemctl --user enable --now scs-daemon
```

## Команды

| Команда | Что делает |
|---|---|
| `scs status` | состояние БД, индекса и эмбеддера |
| `scs repo add <path> --name <n>` | зарегистрировать репозиторий |
| `scs index <repo> [--full]` | проиндексировать (инкрементально по умолчанию) |
| `scs search <repo> <запрос>` | поиск; `-k`, `-m`, `--path`, `--lang` |
| `scs similar <repo> <файл> <строка>` | смысловые дубли фрагмента |
| `scs eval <repo>` | recall@k и MRR на golden-наборе |
| `scs depth <repo>` | ранг ответа в векторной выдаче: провал полноты или ранжирования |
| `scs collapse <repo>` | сколько вызовов инструментов заменяет один search_code |
| `scs history <repo>` | проиндексировать удалённые файлы из истории git |
| `scs export/import <file>` | перенос посчитанных векторов между машинами |
| `scs doctor <repo>` | здоровье индекса: сверка приближённой выдачи с точной |
| `scs gc` | удалить чанки без ссылок |

## Подключение к Claude Code

`.mcp.json` в корне проекта уже настроен. Пять инструментов:

- `search_code` — поиск по смыслу
- `find_similar_code` — дубли логики
- `expand_context` — окрестности фрагмента без чтения файла целиком
- `repo_map` — структура и экспорты
- `index_status` — отличить «такого кода нет» от «индекс устарел»

## Как это устроено

1. **Чанкинг по AST** (TypeScript Compiler API) — по границам функций, классов и типов,
   а не по 500 символов. К каждому чанку добавляется заголовок с путём, экспортами,
   импортами и первой строкой JSDoc; он идёт в модель, но не показывается человеку.
   Markdown/MDX режется по иерархии заголовков — она играет ту же роль, что цепочка
   родителей у метода класса.
2. **Контент-адресуемые вектора**: чанк адресуется хэшем содержимого. Переименование
   файла, `git checkout` и скопипащенный код переиспользуют уже посчитанные вектора.
3. **Эмбеддер за HTTP-контрактом** — TS-ядро не знает, Ollama под ним или Vitis AI
   на NPU. Префиксы модели живут в сервисе, а не в клиенте.
4. **Инкрементальность через `git ls-files -s`** — blob sha всех файлов одной командой,
   без чтения содержимого.
5. **Приоритеты ранжирования**: тесты, фикстуры и карточки файлов понижаются
   множителями (`search.penalties`), потому что почти никогда не являются ответом
   на вопрос «как это работает».

## Измеренное качество

`scs eval`, EmbeddingGemma-300m. Числа сильно зависят от того, кто писал запросы:

| набор | запросов | чанков в индексе | recall@5 | recall@10 | MRR@10 |
|---|---|---|---|---|---|
| фикстура, русские запросы | 14 | 23 | 100% | 100% | 0.964 |
| свой код, в осн. русские | 24 | 268 | 87.5% | 91.7% | 0.806 |
| настроечный, из транскриптов | 58 | 49 185 | 55.2% | 60.3% | 0.420 |
| **отложенный, ни разу не виденный** | **100** | **49 185** | **34.0%** | **46.0%** | **0.229** |

Верить стоит последней строке. Первые два набора писал человек, знавший ответ;
третий собран из 72 транскриптов реальной работы агентов, и запросы в нём намеренно
не содержат слов из имени искомого символа — это верхняя планка сложности, а не
средний вопрос.

Исходная цель «recall@5 ≥ 85%» снята как условие выпуска: измеренного пути к ней
без генеративных моделей в момент запроса нет. Инструмент задуман как **ступень
сужения** (семантика находит точку входа → LSP обходит граф → grep подтверждает),
и в этой роли текущее число рабочее. Разбор с числами — [`docs/RECALL85.md`](docs/RECALL85.md).

**Верить нужно последней строке.** Отложенный набор из 100 запросов был собран
из транскриптов, запечатан и открыт ровно один раз — после заморозки
конфигурации. Разница с настроечным набором в 21 пункт показывает, сколько
в прежних числах было подгонки: третья строка получена на том самом наборе,
на котором подбирались веса, приоритеты, размеры чанков и глубины.

**Приёмка не пройдена**: три из четырёх заранее объявленных порогов не выполнены
(recall@5 34% при пороге 40%, нижняя граница Уилсона 25.5% при 33%, recall@10 46%
при 48%). Пороги подкручивать нельзя — они заморожены до открытия набора.
Разбор провала — [`docs/RECALL85.md`](docs/RECALL85.md).

Путь от 37.9% сложился из независимых слагаемых: ремонт чанкера (треть кодовой базы
вообще не индексировалась, [§19](docs/DESIGN.md)), понижающий приоритет документации,
cross-encoder ([§20](docs/DESIGN.md)), пересборка HNSW, вывод истории git
из общего пространства, назначение модуля в заголовке чанка и размер чанка 500 токенов вместо 300 —
последние два дали +5.1 п.п. к recall@5 и +6.9 к recall@1 без единого обращения
к генеративной модели. Запас ещё есть — `scs depth` показывает ответ в первых
300 кандидатах в 82.8% случаев, — но лежит он не в коэффициентах ранжирования,
а в том, что попадает в вектор.

Реранкер включён по умолчанию и даёт +8.7 п.п. к recall@5. На GPU он стоит
347 мс против 79 без него, на CPU — 3 с, поэтому `npm run cuda:libs` ставит
рядом runtime-библиотеки CUDA 12 (`onnxruntime-node` собран под них, а в системе
13.2), а `npm run rerank:gpu` их подхватывает. Если сервис не поднят, поиск
работает в прежнем порядке и сообщает об этом в stderr.

Сравнение моделей на том же наборе и том же корпусе — [§18](docs/DESIGN.md):

| модель | recall@5 | MRR |
|---|---|---|
| **embeddinggemma-300m** | **37.9%** | **0.227** |
| Qwen3-Embedding-0.6B | 24.1% | 0.163 |
| jina-embeddings-v2-base-code | 5.2% | 0.025 |

Провал модели, заточенной под код, объясняется языком: она англоязычная, а запросы
русские. Гипотезу «потолок межъязыковой» проверили переводом всего набора
на английский — не подтвердилась: 16 из 19 промахов совпали дословно.

Режим по умолчанию — `semantic`. Гибрид с лексическим поиском **замерен и отключён**:
на всех наборах, включая монорепу, он не выиграл ни разу.

### Масштаб

Монорепа в 7178 файлов: индексация 13 минут, 49 185 чанков, ~450 МБ в Postgres,
поиск 90 мс без реранкера и 449 мс с ним (p50).

## Область первого выпуска

**v0.1 — только dev-конфигурация.** Проверено и поддерживается: Linux, Node 22,
PostgreSQL с pgvector, Ollama с `embeddinggemma:300m`, реранкер на CUDA-GPU
(или на CPU, вчетверо медленнее).

**NPU-бэкенд (`services/embed-npu`) — экспериментальный и на железе не проверен.**
Он реализует тот же контракт и на CPU-провайдере даёт вектора, совпадающие
с dev-бэкендом с косинусом 0.993+, но ни разу не запускался на AMD XDNA2.
Доля графа, реально уходящая на NPU, и качество после квантизации проверяются
процедурой в `services/embed-npu/README.md` и до её прохождения считаются
неизвестными.
Повторная индексация после смены чанкера пересчитала лишь половину векторов —
остальные переиспользованы по content_hash.

## Граница архитектуры

**Продукт — чистый retrieval: эмбеддер и cross-encoder, без генеративных моделей
в момент запроса.** Это измеренное решение, а не идеология: локальный LLM-каскад
поднимает recall@5 примерно на 7 п.п., но превращает 90 мс в 40 секунд и требует
6+ ГБ VRAM — то есть противоречит целевой машине с NPU, ради которой и выбрана
модель на 300M параметров.

LLM допустима при индексации (офлайн, результат переносим) и на стороне вызывающей
модели (необязательные поля MCP), но не локально в момент запроса.

## Что осталось

Все запланированные фазы закрыты. Оставшееся — не недописанный код:

- **Открыть отложенный набор.** Он собран (100 запросов) и не открывался:
  `scs eval`, `scs depth`, `scs doctor` и `scs accept` отказываются его читать
  без `--unseal`. Это защита от случайного прогона, а не криптографическая
  печать: переименование файла её обходит, а факт открытия нигде не фиксируется —
  дисциплину держит договорённость. Пороги приёмки заморожены заранее
  ([RECALL85 §4.2](docs/RECALL85.md)); `scs accept` проверяет их сам и возвращает
  ненулевой код при провале. Число выше получено на настроечном наборе, то есть
  на том же, где подбирались параметры.
- **Приёмка NPU-бэкенда на железе.** Написан и проверен на CPU: вектора совпадают
  с dev-бэкендом с косинусом 0.993+. Доля графа на NPU и качество после
  квантизации проверяются только на AMD XDNA2.
- **Кросс-репо поиск** — ждёт сценария, на котором его можно измерить.

## Чего инструмент не чинит

Замер на 45 реальных цепочках разведки из транскриптов (`scs collapse`):
один `search_code` заменяет цепочку в 22% случаев, экономия по числу вызовов —
7.3%. Оценка в §16 была вдвое оптимистичнее. Главная польза не в сокращении
ходов, а в экономии контекста: рой, умерший на лимите, сделал 152 чтения файлов
целиком, и 4000 токенов сфокусированной выдачи вместо файла — это другой
порядок величины, чем 7% вызовов.
