# embed-npu — прод-бэкенд эмбеддера на Ryzen AI

Тот же HTTP-контракт, что у `services/embed-ollama` (§4 проектного документа):
`POST /embed` и `GET /health`. TS-ядро не должно уметь отличить один бэкенд
от другого — переезд между машинами это смена одной строки в конфиге.

> **Статус: проверено на CPU-провайдере, не проверено на NPU.** Машина
> разработки — Intel + NVIDIA, целевая — AMD Strix Point (XDNA2).
>
> Что уже подтверждено настоящим прогоном: контракт целиком, префиксы,
> нормализация, бакеты длин, и главное — **вектора совпадают с dev-бэкендом
> с косинусом 0.993–0.996**, порядок релевантности идентичен.
>
> Что НЕ проверено и до прохождения приёмки считается неработающим: доля графа
> на NPU и качество после квантизации под NPU.
>
> Эта проверка не декоративная: она нашла дефект. Экспорт EmbeddingGemma отдаёт
> два выхода, и ручной mean-pooling по `last_hidden_state` вместо готового
> `sentence_embedding` давал вектора правильной формы и правильной нормы,
> но с косинусом −0.06 к эталону. Проверка формы ответа этого не видит.

## Подготовка модели

```bash
pip install -r requirements.txt

# Готовый экспорт лучше самодельного: fp16 у EmbeddingGemma даёт мусор
# на выходе — не падает, а тихо портит вектора.
huggingface-cli download onnx-community/embeddinggemma-300m-ONNX \
  --local-dir model --include "onnx/model.onnx" "tokenizer.json"
```

**Запрещено:** экспорт в fp16. Активации EmbeddingGemma в float16 не работают
(§2). Допустимы fp32, bf16, q8, q4.

Квантизация под NPU — через Ryzen AI Quantizer (A8W8) либо BF16-флоу.
С версии 1.6 Integer Compiler принимает готовый квантованный ONNX с Hugging
Face без переобучения.

## Запуск

```bash
python server.py                              # CPU: проверка контракта
SCS_NPU_PROVIDER=VitisAI python server.py     # NPU
```

Переменные: `SCS_EMBED_PORT` (8077), `SCS_NPU_MODEL_DIR` (./model),
`SCS_NPU_BATCH` (32), `SCS_EMBED_WS` (collapse|keep), `SCS_VITIS_CONFIG`.

`SCS_EMBED_WS` обязан совпадать с режимом, которым построен индекс: он входит
в идентификатор модели, а тот — в `content_hash` каждого чанка.

## Процедура приёмки

Три проверки, каждая закрывает свой тихий отказ.

**1. Контракт.** На CPU-провайдере:

```bash
python server.py &
python test_contract.py --compare-with http://127.0.0.1:8077
```

Сравнение с эталонным бэкендом обязательно: форма ответа бывает правильной
при полностью неверных векторах. Порог — косинус 0.98; ниже означает сломанный
конвейер (пулинг, префиксы, токенизатор), а не квантизацию.

**2. Доля графа на NPU.** При старте сервис печатает, сколько узлов реально
ушло на DPU. Меньше 70% — это провал компиляции, а не медленная работа:
проверяйте статичность шейпов и бакеты длин. Молча получить 30% и решить,
что «NPU медленный», — самый дорогой из возможных исходов.

**3. Качество против CUDA-эталона.** Главная проверка: квантизация портит
вектора тихо.

```bash
# на машине с NPU, индекс собран этим бэкендом
scs index <repo> --full
scs eval <repo> --golden src/eval/golden.unitify.jsonl --mode semantic
```

Эталон — числа из §20 проектного документа (recall@5 = 46.6% с реранкером,
37.9% без него на `unitify`). **Падение recall@5 больше чем на 3 п.п. означает,
что квантизация испортила вектора**: поднимайте разрядность (A8W8 → BF16).

Косвенная, но более дешёвая проверка — косинус к эталонным векторам:

```bash
python test_contract.py --reference vectors_cuda.jsonl
```

Средний косинус ниже 0.99 к fp32-эталону на тех же входах — тот же сигнал.
